# Target Baseline and Reconnaissance

This document records the initial environment setup, OpenPLC v3 baseline, and host-side reconnaissance performed for AP-01: Unauthorized Control Logic Modification.

The objective is to establish a working target, understand its exposed management interface, and acquire an authenticated session before investigating the program modification and execution workflow.

## 2. Baseline Application

A simple Structured Text program was prepared to establish a known application baseline.

**File:** `baseline_blink.st`

```iecst
PROGRAM BlinkTest
    VAR
        Counter : INT := 0;
        LedOutput : BOOL := FALSE;
    END_VAR

    Counter := Counter + 1;
    IF Counter >= 10 THEN
        LedOutput := NOT LedOutput;
        Counter := 0;
    END_IF;
END_PROGRAM

CONFIGURATION Config0
    RESOURCE Res0 ON PLC
        TASK TaskMain(INTERVAL := T#500ms, PRIORITY := 0);
        PROGRAM Inst0 WITH TaskMain : BlinkTest;
    END_RESOURCE
END_CONFIGURATION
```

## 2.1 Program Behavior

The program increments an internal counter on each task execution. Once the counter reaches ten, it toggles the `LedOutput` Boolean and resets the counter. The task interval is configured to 500 milliseconds, giving a nominal toggle interval of five seconds.

`LedOutput` is an internal variable. This baseline does not establish a physical output mapping or a Modbus address for the variable.

## 2.2 Baseline Workflow

The program was submitted through the OpenPLC management interface using the following workflow:

1. Upload the Structured Text program.
2. Submit the uploaded program for compilation.
3. Inspect the compilation logs.
4. Start the PLC runtime.

The initial packet capture recorded the management-interface requests associated with this workflow, including:

- `POST /upload-program`
- `POST /upload-program-action`
- `GET /compile-program?file=942886.st`
- Repeated requests to `/compilation-logs`
- Runtime log requests
- Requests to `/start_plc`

The `/start_plc` request appeared three times in the capture because the start action was clicked multiple times during the baseline session. This was a user interaction and is not treated as anomalous behavior.

The capture establishes that the management workflow was exercised. Individual HTTP requests alone do not prove successful compilation or the expected runtime behavior.

**Evidence:** `pcaps/baseline_lab.pcap`

## 3. Network Baseline

## 3.1 Baseline Traffic Capture

The initial traffic capture was recorded between the host workstation (`10.97.0.1`) and the OpenPLC target (`10.97.0.103`). Protocol hierarchy analysis identified Ethernet, IPv4, TCP, HTTP, and multipart MIME traffic. The capture contained management-interface interactions associated with program upload, compilation, runtime logs, and PLC startup.

No Modbus protocol traffic was decoded in this baseline capture, and no TCP conversation involving port 502 was identified. The runtime's Modbus TCP listener was confirmed separately through socket inspection.

**Evidence:** `pcaps/baseline_lab.pcap`

## 4. Phase 2: Host-Side Reconnaissance

Reconnaissance was performed from the host workstation using:

```bash
python3 recon_and_acquire.py
```

The script performs perimeter enumeration, HTTP response inspection, endpoint mapping, and authentication testing.

## 4.1 Perimeter Port Enumeration

The target returned the following results:

| Port | State  | Identified service        |
|------|--------|---------------------------|
| 8080 | Open   | HTTP management dashboard |
| 502  | Open   | Modbus TCP runtime        |
| 80   | Closed | HTTP alternate            |
| 22   | Open   | SSH                       |

This confirms that the management interface, Modbus runtime port, and SSH service were reachable from the host workstation. Port reachability alone does not establish whether the runtime accepts unauthorized control operations.

## 4.2 HTTP Response and Security Headers

The management interface was accessed at:

```text
http://10.97.0.103:8080
```

The initial response returned:

| Property     | Observed value               |
|--------------|------------------------------|
| HTTP status  | 200                          |
| Server       | Werkzeug/2.3.7 Python/3.12.3 |
| Content-Type | text/html; charset=utf-8     |

The inspected response did not include the following security headers:

| Header                    | Observation |
|---------------------------|-------------|

| X-XSS-Protection          | Not present |
| Content-Security-Policy   | Not present |
| Strict-Transport-Security | Not present |

These observations describe the inspected HTTP response. They do not independently demonstrate an exploitable vulnerability.

### 4.3 Management Endpoint Mapping

The script checked several application routes without an authenticated session.

| Endpoint    | HTTP status |

| `/login`            | 200 |
| `/dashboard`        | 302 |

These results provide an initial view of the management interface's route structure and unauthenticated access behavior. They do not constitute a complete authorization assessment of every endpoint.

## 4.4 Authentication and Session Acquisition

The reconnaissance script tested the credentials:

```text
Username: admin
Password: openplc
```

The application accepted the credentials and returned a Flask session cookie.

```text
[+] Authentication Successful!
Harvested Session Cookies: {'session': 'redacted'}
```

This confirms that the tested credentials successfully authenticated against the lab instance and that the host-side script could acquire an authenticated session.

The session cookie is redacted in the recorded output. Actual session values should not be included in public research notes or shared evidence.

## 4.5 Packet-Level Reconnaissance Evidence

A separate capture was recorded on the target's `eth0` interface while the host-side reconnaissance script was running. The capture recorded 278 packets, with zero packets dropped by the kernel.

Analysis identified:

- SYN packets originating from `10.97.0.1` and targeting ports 8080, 502, and 22.
- HTTP GET requests corresponding to the endpoint-mapping checks.
- A `POST /login` request during authentication.
- A subsequent `GET /programs` request after the login submission.
- HTTP responses containing session cookies with the `HttpOnly` attribute and expiry timestamps.

The request sequence corroborates the authentication workflow reported by the reconnaissance script. The script's successful authentication result provides the explicit confirmation that the credentials were accepted.

The capture also shows that the session cookie was transmitted over the plain HTTP management connection. This is relevant because an observer with access to the network traffic could potentially obtain session material.

**Evidence:** `pcaps/recon_lab.pcap` (private raw capture).

## 4.6 Metadata-Only Capture

A second capture was created with a 54-byte snapshot length to retain packet headers while truncating packet contents.



Capture verification reported:

| Property            | Result       |
|---------------------|--------------|
| File format         | PCAP         |
| Encapsulation       | Ethernet     |
| Captured packets    | 285          |
| Capture length      | 54 bytes     |
| Capture duration    | 8.68 seconds |
| Kernel packet drops | 0            |

Packet inspection confirmed that original frame lengths, captured lengths, IP addresses, TCP ports, and packet ordering remained available. An HTTP display-filter check returned no decoded HTTP packets.

The capture preserves network-level metadata without retaining complete HTTP payloads. It is suitable as a shareable packet-level evidence artifact after inspection, while the original full capture remains private.

Packets involving TCP port 502 were also present in this capture. This establishes TCP communication with the Modbus listener during reconnaissance.

The metadata capture is a separate capture run, not a sanitized conversion of `recon_lab.pcap`. Its 54-byte snapshot length also should not be treated as an absolute guarantee that every possible sensitive byte is excluded under all packet-header configurations.

**Evidence:** `recon_metadata_only.pcap`.

## 5. Phase 1 and Phase 2 Assessment

The initial environment and reconnaissance establish the following:

- OpenPLC v3 is running inside the isolated Ubuntu virtual machine.
- The web management interface, Modbus TCP port, and SSH service are reachable from the host workstation.
- A baseline Structured Text application was prepared and submitted through the management interface.
- The baseline capture records HTTP upload and compilation-related interactions.
- Unauthenticated requests to several management routes resulted in redirects.
- The tested `admin / openplc` credentials successfully authenticated.
- The host-side script acquired an authenticated Flask session.
- A separate packet capture corroborated the reconnaissance and authentication workflow.
- A truncated metadata-only capture preserved packet-level network evidence without decoding HTTP contents.

These results establish the target environment and provide an authenticated starting point for the next phase. They do not yet demonstrate unauthorized control logic modification, a compilation vulnerability, or remote code execution.


## 7. Next Phase

With the target environment established and an authenticated session acquired, the investigation can move to the program upload and compilation workflow.

The next phase will examine whether control logic can be modified and executed through the management interface, validating each stage with observable evidence.
