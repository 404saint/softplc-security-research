# Control Logic Substitution and Execution

## 1. Objective

This phase investigates whether an attacker with access to the OpenPLC host can replace the active control program, compile modified logic, and cause the runtime to execute it without using the web management interface's normal program-upload workflow.

The experiment targets AP-01: Unauthorized Control Logic Modification.

The objective is to establish whether modified IEC 61131-3 logic can reach the running PLC process through an alternative deployment path and whether its execution can be observed through the Modbus TCP interface.

## 2. Deployment Model and Trust Boundaries

## 2.1 OpenPLC v3 Deployment Model

The target uses OpenPLC v3's runtime-managed deployment architecture.

In its normal workflow, an IEC 61131-3 program is prepared as a Structured Text (`.st`) file and submitted through the runtime's web management interface. The web application receives and stores the program, invokes the compilation toolchain, and makes the resulting logic available to the PLC runtime.

The target therefore combines several responsibilities within the same host environment:

- The Flask-based web application manages programs and runtime operations.
- The IEC 61131-3 compiler translates Structured Text into native code.
- The PLC runtime executes the compiled control logic.
- The Modbus TCP server exposes process-image data to external clients.

The web management interface provides the normal administrative deployment path. The host also exposes SSH, providing a separate route for remote administrative access.

## 2.2 Deployment Path Used in This Experiment

This experiment does not use the normal web-based upload workflow.

Instead, it uses SSH to transfer a program directly to the target host, replaces the active project file, invokes the native compilation wrapper, and restarts the runtime.

The tested deployment path is:

```text
Attacker Workstation
        |
        | SCP over SSH
        v
OpenPLC Host
        |
        | Privileged file replacement
        v
Active Structured Text Project
        |
        | compile_program.sh
        v
MatIEC / Native Compilation
        |
        v
Compiled OpenPLC Runtime
        |
        | Modbus TCP
        v
Holding Register Interface
```

This is a host-level deployment path that bypasses the web application's manual upload interface. The experiment relies on the host's existing administrative capabilities rather than exploiting the web application's upload handler.

## 3. Threat Scenario and Assumptions

## 3.1 Attacker Position

The assumed attacker has network access to the OpenPLC host and has obtained valid SSH credentials for an account capable of performing the required administrative operations.

The attacker does not initially need access to the web management session or its authentication mechanism.

SSH was identified as an exposed service during Phase 2 reconnaissance. Its presence provides a potential remote administration path into the host.

## 3.2 Credential Acquisition Assumption

Credential acquisition is treated as a prerequisite in this experiment, not as a demonstrated exploitation step.

In a real deployment, an attacker might obtain SSH credentials through several routes, including:

- Reuse of credentials exposed through another compromised system.
- Theft of credentials from an administrator's workstation or stored automation configuration.
- Disclosure of credentials through insecure operational practices.
- Compromise of an account through a separate authentication weakness.
- Misuse of legitimate access by an insider or an already compromised administrator account.

These are possible threat scenarios. None was tested or established during this lab. The experiment begins after valid SSH credentials have been obtained.

## 3.3 Required Privileges

SSH authentication alone is insufficient to complete the demonstrated attack.

The deployment procedure also requires privileges to:

- Replace the active OpenPLC project file.
- Execute the compilation toolchain.
- Terminate the existing runtime process.
- Launch the newly compiled runtime.

The PoC obtains these privileges through `sudo`.

Consequently, the demonstrated attack requires an account with sufficient administrative permissions, or another way to obtain those permissions. It does not establish that an ordinary unprivileged SSH account can perform the same operations.

## 3.4 Security Impact

If an attacker obtains the required access, they can substitute the control program independently of the web management interface's normal upload workflow.

The resulting impact can include unauthorized changes to control logic, altered process behavior, and disruption caused by terminating and restarting the PLC runtime.

The actual physical consequences depend on the variables, I/O mappings, connected equipment, and process controlled by the target installation.

## 4. Controlled Experiment

## 4.1 Test Environment

The experiment used the previously established OpenPLC v3 target.

| Property                 | Value                                       |
|--------------------------|---------------------------------------------|
| Target                   | `openplc-target`                            |
| Target IP                | `10.97.0.103`                               |
| Host workstation         | `tesla`                                     |
| Management interface     | TCP 8080                                    |
| SSH                      | TCP 22                                      |
| Modbus TCP               | TCP 502                                     |
| Deployment method        | SSH/SCP and privileged host-side operations |
| PLC programming language | IEC 61131-3 Structured Text                 |

The test was performed within the isolated research environment.

## 4.2 Malicious Payload

The test program was prepared as:

```text
malicious_blink.st
```

The payload uses IEC 61131-3 Structured Text and implements a counter-driven state toggle.

Its relevant behavior is:

- Increment an internal counter during execution.
- Toggle an integer variable after five execution cycles.
- Reset the counter and repeat the sequence.

The variable is declared using located-memory syntax:

```iecst
ExploitTrigger AT %MW0 : INT;
```

This associates the variable with the `%MW0` memory location in the OpenPLC process image.

The purpose of the payload is to create an observable change in a mapped memory location that can be read through the Modbus TCP interface.

## 4.3 Deployment Automation

The deployment procedure was automated using:

```text
deploy_and_verify.py
```

The script combines the following operations:

1. Transfers `malicious_blink.st` to the target user's home directory using SCP.
2. Executes remote commands over SSH.
3. Uses `sudo` to replace the active Structured Text project file.
4. Invokes OpenPLC's native compilation wrapper.
5. Terminates the existing runtime process.
6. Launches the newly compiled runtime in the background.

The script uses `sshpass` and OpenSSH to automate remote authentication and command execution without interactive prompts. It also provides terminal output indicating the progress and completion of each deployment stage.

## 4.4 Compilation Pipeline

The automation invokes OpenPLC's native backend compiler wrapper:

```text
compile_program.sh
```

The compilation output showed the following stages:

- Generation of C source and header files.
- Generation of located-variable information.
- Creation of object files.
- Generation of glue variables.
- Compilation of the main program.
- Completion of the native build.

The generated artifacts included:

```text
POUS.c
POUS.h
LOCATED_VARIABLES.h
VARIABLES.csv
Config0.c
Config0.h
```

The compiler also reported:

```text
Compiling for Linux
Generating object files...
Generating glueVars...
varName: __MW0    varType: INT
Compiling main program...
Compilation finished successfully!
```

The `__MW0` entry is significant because it confirms that the compiler generated a located-variable mapping for the declared `%MW0` variable.

The successful compilation establishes that the modified Structured Text was accepted by the target's native compilation pipeline.

## 4.5 Runtime Replacement

After compilation, the automation terminated the existing runtime process using:

```bash
pkill -f core/openplc
```

It then launched the newly compiled runtime in the background using `nohup`.

This is a process restart, rather than a live runtime hot swap. The existing runtime was terminated and a new process was started with the updated compiled program.

The automation reported:

```text
==================================================
  EXPLOIT DEPLOYED & RUNTIME RELOADED SUCCESSFULLY
==================================================
```

This output records the script's successful completion. The subsequent Modbus test provides the independent runtime-level verification.

## 5. Verification Through Modbus TCP

## 5.1 Baseline Observation

Before deploying the modified program, the holding-register polling test returned zero for both requested registers.

The baseline screenshot records:

```text
[1024]: 0
[1025]: 0
```

This establishes the observed pre-deployment values for the test.

## 5.2 Post-Deployment Polling

After the runtime restart, Modbus polling was performed from the host workstation:

```bash
mbpoll -0 -a 1 -r 1024 -c 2 -t 4 10.97.0.103
```

The command configuration was:

| Parameter | Value |
|---|---|
| Protocol | Modbus TCP |
| Target | `10.97.0.103` |
| TCP port | 502 |
| Slave address | 1 |
| Starting reference | 1024 |
| Register count | 2 |
| Data type | 16-bit holding registers |
| Addressing mode | Zero-based (`-0`) |

The post-deployment output showed:

```text
[1024]: 0
[1025]: 0

[1024]: 1
[1025]: 0

[1024]: 0
[1025]: 0

[1024]: 1
[1025]: 0

[1024]: 0
[1025]: 0

[1024]: 1
[1025]: 0
```

Polling statistics:

```text
6 frames transmitted, 6 received, 0 errors, 0.0% frame loss
```

## 5.3 Register Mapping and Observed Behavior

The compiler output identified the located variable as:

```text
__MW0    INT
```

The Modbus test read holding register 1024, which corresponds to `%MW0` in the tested OpenPLC mapping. The register alternated between zero and one across successive polling cycles. Register 1025 remained zero.

This behavior is consistent with the counter-driven toggle implemented in the injected program. The Modbus responses establish that the runtime was reachable and returning the changing process-image value after deployment.

Together with the compiler's located-variable output, the observations provide evidence that the modified program was compiled, loaded, and executing.

## 6.2 Finding

The experiment demonstrates that an attacker with valid SSH credentials and sufficient administrative privileges can replace the active OpenPLC control program, compile modified logic, and restart the runtime without using the web management interface's manual upload workflow. The injected program's behavior was subsequently observable through the Modbus TCP holding-register interface.

This establishes a host-level control-logic substitution and execution path against the tested OpenPLC v3 deployment.

The important security boundary is the administrative access to the host and its active PLC project. The web management interface is not the only path through which the running control logic can be changed.

## 6.3 Security Implications

The experiment highlights several operational risks:

- **Alternative deployment path:** Host-level access can bypass the normal web-based program-management workflow.
- **Administrative privilege exposure:** An account with sufficient SSH and `sudo` permissions can modify the active PLC project and control the runtime lifecycle.
- **Compilation trust:** The native compilation pipeline accepts and builds the replacement program when invoked with the required privileges.
- **Runtime integrity:** The running control logic can be replaced by terminating the existing runtime and launching a newly compiled version.
- **Process disruption:** The restart operation interrupts the existing runtime, potentially affecting the controlled process.

The attack does not depend on a demonstrated vulnerability in the Flask upload endpoint. It uses an alternative administrative deployment path available on the target.

## 7. Limitations and Scope

The following limitations apply to the results:

1. **Credential acquisition was assumed.** The lab did not demonstrate SSH password theft, brute force, credential reuse, or compromise of an administrator workstation.
2. **Administrative privileges were available.** The experiment does not establish that a standard unprivileged SSH account can replace the active program or restart the runtime.
3. **The test used a software PLC.** No physical PLC hardware, field equipment, or industrial process was connected to the experiment.
4. **The observed effect was limited to the process image.** Modbus polling verified the changing holding-register value. It did not demonstrate a physical actuator or process response.
5. **The experiment used a runtime restart.** It did not demonstrate a live update without interruption.
6. **The tested environment was a single OpenPLC v3 instance.** The results should not automatically be generalized to every OpenPLC deployment or other SoftPLC platform.

The baseline and post-deployment observations support the reported result, but they do not establish the prevalence of this access path in production installations.

## 8. Conclusion

The AP-01 proof of concept successfully demonstrated control-logic substitution and execution through an SSH-based administrative deployment path.

Starting with an assumed set of valid SSH credentials and sufficient privileges, the automation transferred a modified Structured Text program, replaced the active project file, invoked the native compiler, and restarted the OpenPLC runtime.

Compilation output confirmed the generation of the `%MW0` located-variable mapping. Subsequent Modbus TCP polling showed the corresponding holding register alternating between zero and one, consistent with the injected logic executing.

The experiment establishes that control logic in the tested OpenPLC v3 deployment can be changed through direct host-level administrative access, independently of the web management interface's normal upload workflow.

This completes the execution proof for AP-01. Credential acquisition and physical process impact remain outside the demonstrated scope.
