# How PLC Programs Work

 **Research Area:** Software PLC Foundations

 **Investigation:** 04

 **Document Type:** Technical Research Report

 **Research Focus:** How PLC applications are loaded, initialized, scheduled, and executed by a PLC runtime.

--- 

## 1. Scope and Context

A PLC application depends on a runtime to become operational and execute its control logic. The runtime manages the application lifecycle, initializes program data, schedules execution, coordinates I/O operations, and monitors execution conditions.

This investigation examines how a PLC application moves from being loaded into a controller to repeated execution. It focuses on the relationship between the application, runtime, tasks, and I/O interfaces.

The cyclic scan is an important execution model, but it is not the only one. PLC runtimes can support multiple tasks with different scheduling conditions, including cyclic, event-triggered, and freewheeling execution. The available models and their behavior depend on the controller and runtime implementation.

Siemens S7-1200 and CODESYS are used as documented examples of PLC execution behavior. OpenPLC Runtime v4 provides a software PLC reference for understanding application loading, initialization, execution, and runtime extensions.

## 2. Program Loading and Initialization

Before a PLC application can execute, it must be made available to the runtime and prepared for execution. The process varies by platform, but it generally involves application transfer, validation, compilation or loading, initialization, and activation.

### 2.1 Program Loading

Program loading makes an application available to the PLC execution environment. Depending on the platform, the application may be transferred as source files, compiled code, a project archive, or a controller-specific executable format.

The process can involve:

1. Transferring the application from an engineering environment to the controller.
2. Validating the application package and its configuration.
3. Compiling or preparing executable code if required.
4. Loading the executable and its associated data into the runtime.
5. Resolving required runtime functions, libraries, or dependencies.
6. Preparing the application for initialization and execution.

Compilation does not necessarily happen inside the PLC. Some engineering environments compile applications before transferring them, while others allow the target runtime to perform additional compilation or linking.

### 2.2 Application Initialization

Initialization prepares the application and its runtime structures before normal execution begins.

Typical initialization activities include:

- Initializing variables and application data.
- Preparing function-block instances and associated data.
- Restoring retained values where supported.
- Initializing runtime resources and application-specific components.
- Preparing I/O interfaces and configured communication resources.
- Executing configured startup routines.

Variable initialization and retention are important considerations. Non-retained data is generally initialized according to the application's declared initial values or the target's initialization rules. Retained data may preserve selected values across a restart or loss of power, depending on the controller's retention mechanism and configuration.

The exact initialization sequence, including how retained data is restored, is implementation-dependent.

### 2.3 OpenPLC Runtime v4: Loading Example

OpenPLC Runtime v4 documents a compilation and loading process that provides a practical example of these stages [3].

The documented process includes:

1. The OpenPLC Editor prepares and uploads a program archive.
2. The runtime validates and extracts the uploaded files.
3. The runtime compiles the application into a shared library.
4. The current PLC application is stopped.
5. The previous application library is unloaded.
6. The newly compiled library is loaded.
7. The runtime resolves the application's initialization and execution functions.
8. The initialization function is called.
9. The runtime transitions to its running state.

The use of a dynamically loaded shared library is specific to this implementation. Other PLCs may use different executable formats and loading mechanisms.

## 3. PLC Operating States

A PLC controller manages its operating condition and determines whether the user application is permitted to execute.

A familiar operating model consists of STOP, STARTUP, and RUN. These states are documented for Siemens S7-1200 controllers [1].

| Operating state | General behavior |
|---|---|
| STOP | The user control program is not executing. Communication and diagnostic services may remain operational. |
| STARTUP | The controller performs configured initialization and startup activities before normal execution. |
| RUN | The controller executes the configured user application and associated runtime activities. |

### 3.1 STOP

In STOP mode, normal user program execution is suspended. The controller may continue to provide communication, diagnostics, and engineering access.

The behavior of physical outputs during this state depends on controller configuration. A controller may apply substitute values, retain configured output values, or disable outputs.

STOP therefore describes the controller's operating condition, not necessarily the complete shutdown of every runtime service.

### 3.2 STARTUP

Startup prepares the controller to enter normal operation.

On the Siemens S7-1200, startup activities include copying physical input states into input memory, initializing output memory according to the configured behavior, initializing non-retentive data, and executing startup organization blocks.

After the startup routines complete, the controller enters RUN mode and begins its normal program execution cycle [1].

### 3.3 RUN

In RUN mode, the controller executes the configured application according to its execution model.

For a cyclic application, the controller repeatedly processes the configured program. Other tasks, such as event-triggered operations and communication services, may also execute according to their scheduling and priority rules.

### 3.4 Runtime State Models

The three operating modes above are a useful controller-level model, but individual software PLCs may expose different internal states.

OpenPLC Runtime v4 documents states including:

- `EMPTY`
- `INIT`
- `RUNNING`
- `STOPPED`
- `ERROR`

These states describe the runtime's application lifecycle and should not be treated as universal PLC operating modes [3].

The distinction is useful when examining software PLCs because a runtime may have separate states for application availability, initialization, execution, and failure.

## 4. Cyclic Scan Execution

The cyclic scan is a common PLC execution model in which the controller repeatedly executes a configured program.

A simplified representation is:

```text
          ┌────────────────────────┐
          │    Input acquisition   │
          └────────────┬───────────┘
                       │
                       ▼
          ┌────────────────────────┐
          │   Execute control      │
          │        program         │
          └────────────┬───────────┘
                       │
                       ▼
          ┌────────────────────────┐
          │    Output processing   │
          └────────────┬───────────┘
                       │
                       ▼
          ┌────────────────────────┐
          │  Runtime and system    │
          │      processing        │
          └────────────┬───────────┘
                       │
                       └───────────────► Next cycle
```

This diagram illustrates the logical activities involved in cyclic execution. It does not prescribe a universal order for every PLC.

### 4.1 Program Execution

During a scan, the runtime executes the program calls associated with the active task.

The application may contain several Program Organization Units (POUs), functions, and function-block instances. Their execution follows the configured call hierarchy and the order established by the task configuration.

For example, a task may call a main program that subsequently invokes several function blocks. The runtime manages the execution of this call sequence.

### 4.2 Scan Sequence Differences

The order of I/O operations and program execution depends on the controller.

For example, the Siemens S7-1200 documents the following sequence for its normal cyclic execution:

1. Transfer output process-image values to physical outputs.
2. Read physical inputs and update the input process image.
3. Execute the program-cycle organization blocks.
4. Update output values in the process image.
5. Perform runtime diagnostics and other system activities.

Interrupts and communication processing may occur during the scan according to the controller's scheduling rules [1].

This is an important distinction when describing PLC execution. A simplified input-program-output sequence is useful for understanding the concept, but the actual order must be verified against the target controller.

## 5. Input Acquisition and Output Updates

PLC applications interact with physical processes through input and output interfaces. The runtime coordinates these interfaces so that application logic can consume input values and produce output values.

### 5.1 Input Acquisition

Input acquisition is the process of obtaining current values from physical input devices or other configured I/O sources.

Examples include:

- Digital input states from push buttons and limit switches.
- Analog measurements from temperature, pressure, and flow sensors.
- Values received through remote or distributed I/O systems.

A controller may read these values directly from hardware or through an I/O driver and store them in an internal memory area.

### 5.2 Process Image

A process image is an internal memory representation of I/O values. It allows the application to access a consistent set of input and output data during execution.

The input process image contains sampled input values. The output process image contains values calculated by the application before they are transferred to physical outputs.

The general relationship is:

```text
Physical Inputs
      │
      ▼
Input Process Image
      │
      ▼
PLC Application
      │
      ▼
Output Process Image
      │
      ▼
Physical Outputs
```

The Siemens S7-1200 uses process-image memory to provide a snapshot of physical I/O values. Its documentation also describes process-image partitions, which allow selected I/O data to be updated in association with specific interrupt events rather than every normal scan [1].

### 5.3 Output Updates

The application calculates output values during execution. These values are written to the output process image or an equivalent runtime buffer.

The runtime or I/O subsystem subsequently transfers them to the physical output devices.

The timing of this transfer depends on the controller's I/O architecture. An output value calculated during one part of a scan may not reach the physical device until a later update point.

Some controllers also support immediate I/O access, allowing application instructions to read or write physical I/O directly instead of relying exclusively on the process image.

Consequently, the application execution point and the physical I/O update point should be understood as separate parts of the control cycle.

## 6. Tasks and Scheduling

A task determines when configured PLC programs execute. The runtime scheduler manages task activation and determines execution order when multiple tasks are ready.

This builds on the application organization discussed in Investigation 03. A Program POU contains control logic, while task configuration determines when that program is called.

A simplified relationship is:

```text
PLC Configuration
└── Application
    └── Task Configuration
        ├── Task A
        │   ├── Program Instance A
        │   └── Program Instance B
        │
        └── Task B
            └── Program Instance C
```

The exact configuration structure varies between engineering environments.

### 6.1 Common Task Types

CODESYS documents several task types that demonstrate different execution conditions [2].

| Task type | Execution behavior |
|---|---|
| Cyclic | Executes repeatedly at a configured interval. |
| Freewheeling | Executes continuously and starts another cycle after the previous execution completes. |
| Event-triggered | Executes when a configured event occurs. |
| Status-triggered | Executes while a configured condition is true. |

These are examples from CODESYS documentation, not a universal list of task types required by IEC 61131-3.

A controller may support only a subset of these models or implement additional task mechanisms.

### 6.2 Task Priority

When multiple tasks are ready to execute, the scheduler uses task priority and its scheduling rules to determine which task executes first.

CODESYS documents a priority-based processing order. When multiple tasks become ready at the same time, higher-priority tasks are processed first. Tasks with equal priority are processed according to their queue order [2].

The effect of task priority depends on the runtime and underlying execution environment. A higher-priority task may interrupt a lower-priority task, delay its execution, or be scheduled according to other platform-specific rules.

### 6.3 Multiple Tasks

A PLC application can use multiple tasks to execute different parts of its control logic at different intervals or in response to different events.

For example:

- A fast cyclic task may handle time-sensitive control operations.
- A slower cyclic task may process monitoring values.
- An event-triggered task may respond to a configured input or system event.

The task configuration determines which programs are associated with each task and the conditions under which they execute.

Using multiple tasks introduces additional scheduling considerations. Task priorities, execution intervals, shared data, and I/O update behavior can all influence application behavior.

## 7. Execution Timing and Monitoring

Execution timing describes how long a task takes to execute and how consistently it executes relative to its configured schedule.

A PLC application must complete its control operations within the timing constraints established for the process. Simply executing the application quickly is insufficient if its execution timing is unpredictable or inconsistent.

### 7.1 Timing Terminology

| Term | Description |
|---|---|
| Task interval | Configured time between scheduled executions of a cyclic task. |
| Execution time | Time required to execute a task and its associated program calls. |
| Scan time | Time required to complete a scan cycle in a cyclic execution model. |
| Jitter | Variation in the actual timing of task execution relative to its intended schedule. |
| Latency | Delay between an event occurring and the corresponding processing or response. |
| Overrun | A task exceeds its configured execution-time allowance or timing constraint. |

These terms describe different aspects of execution and should not be used interchangeably.

For example, a task configured with a 10 ms interval is scheduled to execute every 10 ms. This does not mean the program itself requires 10 ms to execute.

### 7.2 Execution Time and Scheduling Variation

Actual execution time can vary with application complexity, task scheduling, communication processing, I/O operations, and other runtime activities.

A controller may provide measurements such as minimum, maximum, average, and current execution time. These measurements help identify variations and determine whether a task is consistently completing within its configured timing constraints.

The Siemens S7-1200, for example, monitors minimum and maximum scan-cycle times. Its documentation notes that scan duration can vary depending on the user program and communication tasks [1].

### 7.3 Watchdogs and Timing Overruns

A watchdog monitors execution against a configured time limit. It helps detect tasks that take too long to complete or fail to execute as expected.

The response to a watchdog event depends on the controller and runtime configuration. Possible responses include:

- Reporting a task or timing error.
- Triggering a configured error-handling routine.
- Stopping the affected application.
- Transitioning the controller to STOP mode.
- Applying configured output behavior.

For example, the Siemens S7-1200 monitors its maximum scan-cycle time and can generate a time-error event when that limit is exceeded. The controller's response depends on its configured error-handling behavior [1].

CODESYS also supports watchdog configuration in its task settings [2].

A watchdog is therefore a monitoring and fault-handling mechanism. Its presence alone does not guarantee that a control application will always meet its real-time requirements.

### 7.4 Timing and Control Behavior

Execution timing directly influences how quickly a PLC can respond to changes in the physical process.

Consider a digital input that changes state between two input sampling points. The application may not process the new value until the next applicable input update and task execution. The resulting response delay depends on the input update mechanism, task interval, scheduling behavior, program execution time, and output update timing.

For this reason, timing analysis should consider the complete path from input acquisition through program execution to the physical output update.

## 8. PLC Runtime Responsibilities

The PLC runtime provides the environment in which the control application operates. Its responsibilities extend beyond calling the user program.

The following table summarizes common runtime responsibilities. Their implementation and distribution vary across PLC platforms.

| Responsibility | Description |
|---|---|
| Program loading | Makes the application executable available to the runtime. |
| Initialization | Prepares application data, instances, and required resources. |
| State management | Manages application and controller operating states. |
| Task scheduling | Determines when configured programs execute. |
| Program execution | Executes application code and associated POUs. |
| I/O handling | Coordinates input acquisition and output updates through configured interfaces and drivers. |
| Runtime services | Provides services required by application execution, such as memory and timing support. |
| Diagnostics | Reports execution status, runtime errors, and controller conditions. |
| Timing monitoring | Tracks execution timing and detects configured timing violations. |
| Data retention | Preserves or restores retained application values where supported. |

These responsibilities may be implemented by one runtime process or distributed across several components.

### 8.1 OpenPLC Runtime v4 Architecture

OpenPLC Runtime v4 provides a practical example of a software PLC with separate management and execution components [4].

Its documented architecture includes:

- **REST API server:** A Python-based management interface used by the OpenPLC Editor to upload programs, monitor compilation, and control execution.
- **PLC runtime core:** A C/C++ component responsible for executing the loaded PLC application.
- **Plugin system:** An extension mechanism for hardware drivers, communication protocols, and other runtime integrations.

This separation demonstrates that application management and control execution can be handled by different runtime components.

### 8.2 Runtime Extensions and I/O Coordination

OpenPLC's native plugin system provides optional `cycle_start()` and `cycle_end()` hooks [5].

These hooks are synchronized with the PLC scan cycle:

- `cycle_start()` executes before PLC application logic.
- `cycle_end()` executes after PLC application logic.

They allow plugins to coordinate I/O operations with application execution. For example, a plugin can prepare input data before the application runs and process output data after the application completes its scan.

The plugin documentation also distinguishes these synchronized hooks from operations performed independently by plugin threads. This demonstrates how I/O drivers and runtime extensions can participate directly in the application execution cycle.

The plugin hooks are an OpenPLC-specific implementation detail. Other PLC runtimes may coordinate I/O through different mechanisms.

## 9. Technical Assessment

PLC program execution is a coordinated process managed by the runtime. The application must be loaded and initialized before it can execute, and its execution depends on the controller's operating state and configured tasks.

The cyclic scan provides a useful model for understanding repeated control execution, but actual implementations may use multiple tasks, event-driven execution, interrupts, and different I/O update mechanisms.

Input acquisition and output processing are integral to this process. The values used by application logic may come from process-image memory or direct I/O access, while calculated outputs may be transferred to physical devices at a later point in the cycle.

Execution timing is equally important. Task intervals, execution time, scheduling variation, latency, and watchdog behavior influence how consistently the controller responds to the physical process.

For software PLCs, these activities are provided by the runtime and its associated components. Understanding their responsibilities establishes a foundation for examining how control applications interact with the software environment in which they execute.
