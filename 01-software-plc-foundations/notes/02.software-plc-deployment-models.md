# Software PLC Deployment Models

**Research Area:** Software PLC Foundations  
**Investigation:** 02  
**Document Type:** Technical Research Report  
**Research Focus:** Deployment architectures, host environments, resource dependencies, and security boundaries

---

## 1. Scope and Context

Software PLCs implement industrial control functionality through software runtimes operating on compatible computing platforms. Unlike a dedicated hardware PLC, the runtime can be deployed in different computing environments, each with its own resource management, execution, networking, and isolation characteristics.

The deployment model determines how the PLC runtime accesses computing resources, interacts with industrial devices, and depends on the underlying infrastructure. These factors influence operational reliability, system integration, and the boundaries that must be considered during a security assessment.

This investigation examines common software PLC deployment models, including direct hardware deployments, virtual machines, and containers. It also considers industrial PCs, edge computing environments, host resource dependencies, and network placement.

CODESYS, Siemens SIMATIC S7-1500 Virtual Controller, and OpenPLC Runtime v4 are used as implementation references.

### 1.1 Deployment Terminology

| Term                   | Description                                                                                                  |
|------------------------|--------------------------------------------------------------------------------------------------------------|
| Bare-metal execution   | Software operating directly on physical hardware without a conventional host operating system or hypervisor. |
| Native host deployment | A PLC runtime installed directly on a host operating system.                                                 |
| Real-Time Operating System (RTOS) | An operating system designed to provide predictable task scheduling and response behavior.        |
| Virtual Machine (VM)   | A software-defined computing environment that presents virtual hardware to a guest operating system.         |
| Hypervisor             | Software that creates and manages virtual machines and allocates underlying hardware resources.              |
| Container              | An isolated application environment that uses the host operating system's kernel.                            |
| Industrial PC (IPC)    | An industrial computing platform designed for deployment in industrial environments.                         |
| Edge Computing         | A deployment context in which computing and application services operate close to the devices or processes generating data. |
| Resource Isolation     | Mechanisms that restrict or dedicate computing resources to particular applications or execution environments. |
| Network Isolation      | Mechanisms that restrict or separate communication between systems, applications, or network segments.       |

The term *bare-metal* requires particular care. A bare-metal hypervisor is installed directly on physical hardware, but PLC runtimes executing inside its virtual machines are still virtualized deployments. Similarly, a PLC runtime installed directly on Linux is a native host deployment, not strict bare-metal execution.

## 2. Direct Hardware Deployment

A direct hardware deployment places the PLC runtime on a physical computing platform without an intervening virtual machine or container.

This arrangement can take different forms depending on the system software used by the platform.

### 2.1 Strict Bare-Metal Execution

In a strict bare-metal arrangement, software executes directly on physical hardware without a conventional host operating system or hypervisor.

The software is responsible for managing the hardware resources and providing the functionality required by the control application.

A simplified architecture is:

```text
       Control Application
                |
         PLC Runtime
                |
      Hardware Management
                |
        Physical Hardware
                |
         Industrial I/O
```

This arrangement gives the software direct responsibility for hardware interaction and resource management. It also places greater importance on hardware compatibility, device support, and the implementation of scheduling and I/O functionality.

Strict bare-metal execution should not be assumed to be the standard deployment approach for every software PLC.

### 2.2 RTOS-Based Deployment

An RTOS-based deployment runs the PLC runtime within a real-time operating system installed on the physical computing platform.

```text
       Control Application
                |
         PLC Runtime
                |
              RTOS
                |
        Physical Hardware
                |
         Industrial I/O
```

The RTOS provides services such as task scheduling, synchronization, memory management, and hardware access.

This model can provide a controlled execution environment without requiring a general-purpose desktop operating system. Its real-time characteristics depend on the RTOS, hardware platform, runtime implementation, and system configuration.

An RTOS is an operating system, so this arrangement is a direct hardware deployment but not strict bare-metal execution.

### 2.3 Native Host Deployment

A native host deployment installs the PLC runtime directly on the operating system of a physical computer.

For example, a runtime may operate as a process or set of services on a Linux-based industrial PC.

```text
       Control Application
                |
         PLC Runtime
                |
       Host Operating System
                |
          Host Hardware
                |
         Industrial I/O
```

The runtime uses operating system services for process execution, memory management, device access, and networking.

This arrangement can simplify software installation and integration with existing host services. However, the runtime also inherits dependencies on the host operating system, its configuration, and supporting software.

A native deployment does not automatically provide deterministic execution. Scheduling behavior, processor availability, driver implementation, and competing workloads remain relevant.

### 2.4 Architectural Considerations

Direct hardware deployments avoid the additional abstraction introduced by virtual machines and containers. However, their execution and isolation characteristics still depend on the underlying system software.

| Consideration        | Architectural Implication                                                                          |
|----------------------|----------------------------------------------------------------------------------------------------|
| Hardware Access      | Runtime interacts with physical devices through the available system environment.                  |
| Resource Management  | CPU, memory, and I/O resources are managed by the runtime, operating system, or platform software. |
| Runtime Dependencies | Depends on the selected execution environment and supporting components.                           |
| Isolation            | Depends on the operating system, runtime architecture, and platform configuration.                 |
| Maintenance          | May involve updates to the operating system, runtime, firmware, and device drivers.                |

## 3. Virtual Machine Deployment

A virtual machine deployment runs a PLC runtime inside a virtualized computing environment. The hypervisor provides virtual hardware to the guest system and manages access to the physical host's resources.

### 3.1 VM Architecture

A typical software PLC virtual machine consists of a guest operating system, PLC runtime, control application, and virtual interfaces.

```text
          Control Application
                   |
             PLC Runtime
                   |
            Guest Operating
                 System
                   |
             Virtual Hardware
                   |
              Hypervisor
                   |
             Host Hardware
                   |
          Physical I/O / Network
```

The guest operating system provides the environment required by the PLC runtime. The hypervisor manages the virtual machine's access to processor, memory, storage, and supported hardware devices.

Depending on the implementation, physical devices may be accessed through virtualized interfaces, device passthrough, or dedicated hardware assignments.

### 3.2 Resource Allocation

Virtual machines use resources allocated by the hypervisor.

Relevant resources include:

- Virtual CPUs and processor scheduling.
- Guest memory allocation and reservation.
- Virtual storage devices.
- Virtual network interfaces.
- Physical device passthrough.
- Hardware-assisted virtualization features.

Resource allocation influences the execution environment of the PLC runtime.

For example, CPU contention between virtual machines may affect task scheduling. Memory overcommitment and host-level resource pressure can also influence runtime availability.

Some industrial virtual PLC implementations use dedicated processor cores, memory reservations, and hardware-assisted device access to reduce interference from other workloads.

These mechanisms must be evaluated as part of the complete deployment configuration.

### 3.3 Implementation Reference: Siemens SIMATIC S7-1500 Virtual Controller

Siemens provides a virtual PLC implementation through the SIMATIC S7-1500 Virtual Controller CPU 151xV.

The controller is delivered as an Industrial Edge application and deployed to a supported Industrial Edge device through Industrial Edge Management.

Its deployment uses an Industrial Edge Virtual Device and a hypervisor-based infrastructure. Siemens documents requirements for CPU core isolation and network interface isolation during deployment [10].

The real-time configuration also includes hypervisor-specific settings. Siemens documents CPU and memory reservations and latency-sensitivity configuration for VMware ESXi. These settings are required for the documented deterministic real-time configuration [11].

This implementation demonstrates that a virtual PLC can use dedicated computing resources and network isolation rather than relying solely on shared host resources.

The deployment also introduces dependencies on the Industrial Edge device, management infrastructure, hypervisor configuration, and associated network interfaces.

The documented ESXi settings apply to the Siemens implementation and should not be generalized to all virtual PLC deployments.

### 3.4 Virtualization Security Boundaries

Virtualization introduces separation between the guest operating system and the host environment. The hypervisor mediates access to the physical hardware and provides the isolation boundary between virtual machines.

However, this separation depends on correct configuration and the security of the underlying virtualization platform.

Relevant considerations include:

- Hypervisor integrity and administrative access.
- Guest operating system security.
- Virtual network configuration.
- Shared storage and management interfaces.
- Device passthrough and hardware access.
- Resource allocation and contention.
- Virtual machine snapshots, backups, and images.

A compromise of the guest operating system may affect the PLC runtime and control application within that VM. A compromise of the hypervisor or virtualization management environment can have a broader impact across hosted systems.

NIST SP 800-125A Rev. 1 provides security recommendations for server-based hypervisor platforms, while SP 800-125B addresses secure virtual network configuration [3][4].

## 4. Containerized Deployment

Containerized deployment packages a PLC runtime and its supporting application components into a container image.

Unlike a virtual machine, a container does not normally include a separate guest operating system kernel. It uses the host operating system's kernel while relying on operating system mechanisms to provide process and resource isolation.

### 4.1 Container Architecture

A typical containerized PLC deployment can be represented as follows:

```text
        +----------------------------+
        |        Host System         |
        |                            |
        |    Host Operating System   |
        |              |             |
        |       Container Engine     |
        |              |             |
        |    +------------------+    |
        |    |  PLC Container   |    |
        |    |                  |    |
        |    |  PLC Runtime     |    |
        |    |       |          |    |
        |    |  Control App     |    |
        |    |       |          |    |
        |    |  Runtime Deps.   |    |
        |    +------------------+    |
        |              |             |
        +--------------+-------------+
                       |
                 Host Interfaces
                       |
                 Industrial I/O
```

The container engine manages container creation, execution, networking, storage, and resource configuration.

The PLC runtime executes within the container environment, while the host operating system provides the underlying kernel and hardware access.

### 4.2 Host and Container Relationship

Containers provide application-level isolation, but they do not create the same hardware and operating-system boundary as a virtual machine.

The container shares the host kernel. Consequently, kernel vulnerabilities, privileged container configurations, and excessive device access can weaken the separation between the application and host.

Container security also depends on the configuration of namespaces, control groups, capabilities, filesystem permissions, mounted volumes, and network interfaces.

| Component                | Responsibility                                                                            |
|--------------------------|-------------------------------------------------------------------------------------------|
| Host Kernel              | Provides the kernel functionality used by the container.-                                 |
| Container Engine         | Creates and manages container environments.                                               |
| Namespaces               | Provide isolation of selected system resources, such as processes and network interfaces. |
| Control Groups (cgroups) | Account for and constrain resource usage.                                                 |
| Container Image          | Packages the runtime and its application dependencies.                                    |
| Mounted Volumes          | Provide access to persistent or host-managed data.                                        |
| Container Network        | Provides communication between the container, host, and other systems.                    |

Container isolation should not be treated as a complete security boundary by default. Its effectiveness depends on the privileges and resources granted to the container.

### 4.3 Implementation Reference: CODESYS Virtual Control for Linux SL

CODESYS Virtual Control for Linux SL provides an example of a containerized PLC runtime.

The product uses container technology, supporting deployment through Docker or Podman on compatible Linux platforms [8][9].

This arrangement separates the PLC runtime from the host's general application environment while retaining the host kernel and hardware as shared infrastructure.

The deployment therefore depends on the host Linux system, container engine, runtime image, and required hardware interfaces.

The use of containers does not by itself establish real-time execution characteristics. These depend on the host platform, runtime configuration, resource allocation, and supported real-time mechanisms.

### 4.4 Container Resource Management

Containers can be configured with resource constraints that control their access to host resources.

Relevant controls include:

- CPU quotas and CPU affinity.
- Memory limits and reservations.
- Process limits.
- Device access permissions.
- Filesystem mounts.
- Container capabilities.

Without suitable constraints, a container may consume resources needed by other applications on the host.

For a PLC runtime, resource contention can affect application availability and execution timing. Resource limits must therefore be configured with the control application's requirements in mind.

### 4.5 Container Networking

Container networking determines how the PLC runtime communicates with the host, other containers, and external industrial systems.

Docker provides several network drivers with different connectivity and isolation characteristics [6].

| Network Mode | Architectural Behavior | Security Consideration |
|---           |---                     |---                     |
| Bridge       | The container connects to a software bridge and receives a network interface. Containers on the same bridge can communicate. | Published ports can forward traffic from host addresses to container ports. Control published ports and host firewall rules. |
| Host         | The container shares the host's network namespace and uses the host's network interfaces directly. | Network isolation between the container and host is removed. Port publishing has no effect. |
| Macvlan      | The container receives its own MAC address and can appear as a separate device on the physical network. | Requires careful physical network and switch configuration. |
| Overlay      | Connects containers across multiple Docker hosts, allowing communication across nodes. | Introduces distributed network configuration and additional communication paths. |
| None         | The container has no normal external network connectivity and retains only loopback. | External communication is unavailable unless additional interfaces or mechanisms are configured. |

Published ports are particularly relevant to containerized PLC deployments. A service running inside a container may become accessible through a host interface when its port is published.

For example, publishing a runtime management port can expose its service to systems outside the container. The actual exposure depends on the published address, firewall configuration, host interfaces, and network placement [7].

The selected network mode should reflect the required communication paths between engineering systems, PLC runtimes, and industrial devices.

### 4.6 Container Security Boundaries

The security boundary of a containerized PLC extends beyond the runtime itself.

Relevant components include:

- Host operating system and kernel.
- Container engine and its administrative interface.
- Container image and software dependencies.
- Runtime process privileges.
- Mounted host directories and persistent storage.
- Device mappings and hardware access.
- Container network configuration.
- External management and engineering interfaces.

A container compromise may affect the host if the container has excessive privileges, unsafe mounts, or access to sensitive host resources. A host compromise can also affect the runtime and other containers operating on that host.

## 5. Industrial PCs and Edge Computing

Industrial PCs and edge computing environments are relevant to software PLC deployments because they provide computing platforms closer to industrial processes and equipment.

These terms describe the computing platform and deployment context. They do not define a specific PLC execution model.

### 5.1 Industrial PCs

An Industrial PC is a computing platform designed for industrial applications.

Depending on its intended use, an IPC may provide:

- Industrial power and connectivity options.
- Extended operating temperature ranges.
- Mechanical and environmental protection.
- Industrial communication interfaces.
- Expansion capabilities.
- Support for embedded or general-purpose operating systems.

A software PLC can operate directly on an IPC, inside a virtual machine, or within a container, provided that the platform supports the selected runtime and deployment requirements.

An IPC should not automatically be assumed to meet every industrial environmental or reliability requirement. Its suitability depends on its specifications, qualification, installation conditions, and intended application.

IEC 61131-2 provides equipment requirements and tests relevant to programmable controller equipment and associated peripherals [1].

### 5.2 Edge Computing

Edge computing places computing and application services closer to the devices or processes generating data.

In industrial environments, this may involve deploying applications on industrial PCs, gateways, edge servers, or other computing devices located near production systems.

Related concepts such as fog computing extend processing, management, and analytics into distributed network infrastructure. NIST SP 500-325 provides a conceptual model for fog computing and its relationship with cloud-based computing [2].

In this investigation, *edge computing* describes a deployment context rather than a specific execution architecture. A PLC runtime at the edge may operate natively, inside a VM, or in a container.

### 5.3 Example Industrial Deployment Context

The following diagram illustrates a simplified industrial computing arrangement. It is an architectural example, not a standardized deployment model.

```text
              Enterprise Environment
                       |
                Enterprise Network
                       |
              Industrial Platform
                       |
               Industrial Network
                       |
              Edge Computing Layer
                       |
            +----------------------+
            | Industrial PC / Edge |
            |       Platform       |
            |                      |
            |   PLC Runtime        |
            |   Management Apps    |
            |   Data Services      |
            +----------------------+
                       |
                Control Network
                       |
             Remote / Local I/O
                       |
                Industrial Process
```

The exact placement of PLC runtimes, management services, and data-processing applications depends on the control architecture and operational requirements.

The separation between enterprise, industrial, and control networks should be designed according to the communication requirements and security boundaries of the deployment.

### 5.4 Operational and Security Considerations

Industrial PC and edge deployments can consolidate multiple applications and services on a shared computing platform.

This can simplify integration and data processing, but it also creates dependencies between applications that may have different availability, performance, and security requirements.

Relevant considerations include:

- Separation of control and non-control workloads.
- Access to physical and network interfaces.
- Host operating system maintenance.
- Application and runtime lifecycle management.
- Resource allocation and contention.
- Physical access to edge devices.
- Remote administration and update mechanisms.
- Network segmentation and communication restrictions.

A failure or compromise of a shared edge platform may affect several applications. The impact depends on their execution environments, resource separation, privileges, and network connectivity.

## 6. Host Resources and Runtime Dependencies

Regardless of deployment model, a software PLC depends on computing resources and supporting components to execute its control application.

The way these resources are provided and isolated differs between direct hardware, virtual machine, and containerized deployments.

### 6.1 Computing Resources

| Resource           | Deployment Consideration                                                                       |
|--------------------|------------------------------------------------------------------------------------------------|
| CPU                | Processor availability and scheduling influence execution timing and workload capacity.        |
| Memory             | Insufficient memory can affect runtime stability and application availability.                 | 
| Storage            | Runtime files, application programs, configuration, logs, and persistent data require storage. |
| Network Interfaces | Communication depends on physical or virtual interfaces and their configuration.               |
| I/O Devices        | Access may require drivers, device mappings, passthrough, or remote communication.             |
| System Services    | Runtime operation may depend on operating system services and supporting processes.            |

### 6.2 Runtime Dependencies

A software PLC may depend on several layers of software and infrastructure.

```text
             Control Application
                      |
                 PLC Runtime
                      |
          Runtime Libraries / Drivers
                      |
       Operating System / Guest OS / RTOS
                      |
       Hypervisor / Container Engine
                      |
                Host Hardware
```

This diagram represents a generalized dependency chain. Not every deployment contains all of these layers. For example, a native host deployment does not require a hypervisor or container engine.

The dependency chain is important because a failure or compromise in a supporting component may affect the PLC runtime.

### 6.3 Resource Contention and Availability

Resource contention occurs when multiple processes or applications compete for limited computing resources.

In software PLC deployments, competing workloads may include:

- Data collection and historian services.
- Engineering and management applications.
- Network services.
- Monitoring and logging agents.
- Other PLC runtime instances.
- General-purpose host applications.

The effects depend on resource allocation, scheduling, isolation, and workload behavior.

Resource constraints can reduce the risk of one application consuming all available host resources, but they do not independently guarantee deterministic execution.

The complete system must be evaluated against the control application's timing, availability, and reliability requirements.

## 7. Network Placement and Isolation

Network placement determines how a software PLC communicates with engineering systems, other controllers, remote I/O, supervisory applications, and enterprise infrastructure.

The deployment model influences the network interfaces available to the runtime and the mechanisms used to isolate its communication.

### 7.1 Network Placement

A software PLC may communicate through:

- Physical host network interfaces.
- Virtual machine network adapters.
- Container network interfaces.
- Dedicated or passed-through network devices.
- Remote industrial I/O connections.

The network path may include several layers of virtual switching, routing, firewalling, or address translation before reaching the physical network.

Consequently, the network configuration of the runtime must be considered together with the host and virtualization or container infrastructure.

### 7.2 Network Isolation

Network isolation separates communication paths to restrict unnecessary access between systems.

Possible mechanisms include:

- Physical network separation.
- VLAN segmentation.
- Virtual switches and port groups.
- Host firewall rules.
- Container network separation.
- Dedicated network interfaces.
- Hypervisor-managed network isolation.
- Industrial firewalls and access-control rules.

Isolation should be based on required communication paths rather than relying solely on the deployment model.

For example, a container attached to a bridge network may have limited direct connectivity, but published ports can expose its services through the host. A VM may have a separate virtual network interface, but its connectivity still depends on virtual switch and physical network configuration.

### 7.3 Management and Control Communication

Software PLC deployments may expose different communication paths for management and control.

| Communication Type                | Purpose                                           | Security Consideration                             |
|-----------------------------------|---------------------------------------------------|----------------------------------------------------|
| Engineering Communication         | Program development, transfer, and configuration. | Restrict access to authorized engineering systems. |
| Runtime Management                | Start, stop, configure, and monitor the runtime.  | Protect management APIs and administrative interfaces. |
| Industrial Protocol Communication | Exchange process data with controllers, I/O, and other devices. | Restrict access according to operational requirements. |
| Monitoring and Diagnostics        | Collect runtime status, logs, and system information. | Prevent unauthorized access or disclosure of operational information. |
| Host Administration               | Manage the operating system, hypervisor, or container engine. | Restrict administrative access because it may provide control over the runtime environment. |

The management plane and control communication paths should be considered separately during architecture and security assessments, even when they share physical network infrastructure.

## 8. Existing OpenPLC Deployment: Host Relationship

This section uses observations from the previously established OpenPLC Runtime v4.3.1 lab. No additional deployment or lab execution was required for this investigation.

The objective is to relate the existing runtime to its container and host environment.

### 8.1 Deployment Context

The existing lab used the OpenPLC Runtime v4.3.1 container image published by Autonomy Logic [12][13].

The runtime was deployed through Docker on a Linux host.

The runtime reported version `v4.3.1` through its API. The release corresponds to commit `8d69d93` [13].

This establishes the deployment as a containerized software PLC running on a Linux host.

### 8.2 Host and Runtime Relationship

The observed deployment can be represented as follows:

```text
                 Linux Host
                     |
              Host Operating
                  System
                     |
              Docker Engine
                     |
          +----------------------+
          |   OpenPLC Runtime    |
          |       v4.3.1         |
          |                      |
          |   Management Service |
          |          |           |
          |    PLC Runtime Core  |
          |          |           |
          |   Control Application|
          +----------------------+
                     |
             Container Interfaces
                     |
             Host / Network I/O
```

The diagram represents the deployment relationship at a logical level. It does not assert a specific Docker network mode or exact host interface configuration.

The container shares the host Linux kernel. Docker provides the container environment and manages its process, networking, and resource configuration.

The runtime's management functionality and PLC execution core are implemented as separate components. Their separation is part of the OpenPLC v4 architecture.

### 8.3 Observed and Established Characteristics

| Characteristic     | Existing Observation                                  | Limitation                                                   |
|--------------------|-------------------------------------------------------|--------------------------------------------------------------|
| Host environment   | Linux host running Docker                             | Host configuration was not comprehensively assessed          |
| Runtime processes  | Python management process, `etherdog`, and `plc_main` | Process state reflects the captured lab session              |
| Network listeners  | TCP `8443` and UDP `33333` observed                   | No `502` listener in the inspected snapshot                  |
| Port publishing    | TCP `8443` and `502` published                        | Publishing does not establish application-level availability |
| Network mode       | Not identified                                        | Docker network driver was not established                    |
| CPU affinity       | CPU mask `fff`                                        | Describes the inspected process affinity                     |
| Resource limits    | No CPU quota or memory maximum reported by the inspected cgroup files | Parent cgroups and host-level constraints were not ruled out |
| Scheduling         | `SCHED_OTHER`; `SCHED_FIFO` request failed            | No timing accuracy or jitter measurements performed           |
| Device interfaces  | Standard device nodes observed; no obvious dedicated GPIO, SPI, or I²C nodes | Does not rule out other I/O mechanisms |
| Persistent storage | Not established                                       | Complete mount and volume configuration was not documented    |

### 8.4 Security Boundary Assessment

The OpenPLC deployment demonstrates that a containerized PLC runtime remains dependent on its host environment.

The relevant security boundary includes the Linux host, Docker engine, container configuration, runtime processes, and communication interfaces.

The container provides process and resource isolation mechanisms, but it does not have an independent kernel. Its security therefore depends partly on the host kernel and the permissions granted to the container.

The following areas are relevant to a security assessment:

- Host operating system integrity.
- Docker daemon and administrative access.
- Container privileges and capabilities.
- Mounted files and persistent application data.
- Runtime management interfaces.
- Container network configuration.
- Resource constraints and availability.
- Access to physical or remote I/O interfaces.

The existing lab establishes the general host-to-container relationship. It does not establish the exact configuration or security posture of every boundary listed above.

No additional conclusions about network exposure, privilege level, resource limits, or device access should be made without the corresponding deployment configuration.

## 9. Technical Assessment

Software PLC deployment models determine how the PLC runtime is hosted, how computing resources are provided, and where the relevant security boundaries exist.

Direct hardware deployments place the runtime on physical computing platforms without an intervening VM or container. Their characteristics depend on the selected operating environment, hardware interfaces, and resource management mechanisms.

Virtual machine deployments introduce a hypervisor layer that manages virtual hardware and separates guest environments. They can support dedicated resource allocation and network isolation, but also introduce dependencies on the hypervisor and virtualization management infrastructure.

Containerized deployments package the runtime and its dependencies while sharing the host kernel. They provide application-level isolation and deployment flexibility, but their security depends on container configuration, host integrity, and the resources made available to the container.

Industrial PCs and edge environments provide deployment contexts for these models. They do not prescribe a particular runtime architecture or isolation mechanism.

The most relevant distinctions are:

**1. Execution environment:** A runtime may execute directly on hardware, within an operating system, inside a virtual machine, or within a container.

**2. Resource dependency:** Every deployment depends on physical computing resources, but the mechanisms used to allocate and isolate them differ.

**3. Network placement:** Physical, virtual, and container interfaces determine how the runtime communicates with engineering systems, industrial devices, and other networks.

**4. Security boundaries:** Each deployment introduces different dependencies and administrative interfaces that must be included in the security assessment.

The existing OpenPLC deployment provides a practical example of a containerized runtime and its relationship with the Linux host. It also establishes a baseline for examining how runtime components, host resources, and network interfaces interact.

These deployment characteristics provide the context for the next investigation, which examines industrial control logic and the programming languages used to define PLC applications.
