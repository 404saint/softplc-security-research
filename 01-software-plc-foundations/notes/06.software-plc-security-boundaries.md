# Software PLC Security Boundaries

**Research Area:** Software PLC Foundations \
**Investigation:** 06 \
**Document Type:** Technical Research Report \
**Research Focus:** Establishing the security architecture of software PLC environments by identifying their components, trust relationships, interfaces, and boundaries.

---

## 1. Scope and Context

A software PLC environment consists of several components that work together to develop, deploy, execute, and manage industrial control applications. Its security depends on the relationships between these components, the privileges they operate with, and the interfaces through which they communicate.

Unlike a traditional PLC with an integrated hardware and firmware platform, a software PLC may depend on a general-purpose operating system, a container engine, a hypervisor, external libraries, and other host services. These dependencies introduce additional trust relationships that must be considered when assessing its security architecture.

This investigation examines the security boundaries within software PLC environments, including the host operating system, runtime, engineering workstation, control application, management interfaces, and industrial network. OpenPLC Runtime v4.3.1 is used as a practical reference to relate these concepts to an existing deployment.

The objective is to establish the components and trust relationships that define the software PLC attack surface. This is an architectural assessment, not a vulnerability assessment or an evaluation of exploitability.

## 2. Software PLC Security Architecture

### 2.1 Components and Trust Boundaries

A software PLC environment can be represented as a collection of interconnected components:

- **Physical hardware:** Provides processing, memory, storage, networking, and physical I/O resources.
- **Host firmware:** Initializes hardware and provides platform-level configuration and services.
- **Host operating system:** Manages processes, memory, filesystems, networking, and access to hardware.
- **Isolation environment:** A hypervisor or container engine may provide separation between the PLC runtime and other workloads.
- **PLC runtime:** Loads, initializes, and executes control applications while coordinating runtime services.
- **Control application:** Contains the program logic and configuration that determine control behavior.
- **Engineering environment:** Provides the tools used to develop, compile, transfer, monitor, and maintain PLC applications.
- **Management interfaces:** Allow authorized users and engineering tools to interact with the runtime.
- **Industrial interfaces:** Connect the runtime to HMIs, remote I/O, field devices, and other industrial systems.

These components form several trust boundaries. The exact boundaries depend on the deployment architecture and the security mechanisms implemented by the platform.

For example, a native Linux deployment places the runtime directly within the host operating system's process environment. A containerized deployment adds container isolation mechanisms but continues to share the host kernel. A virtual-machine deployment introduces a guest operating system and hypervisor boundary.

### 2.2 Trust Relationships

The security of one component often depends on the integrity and availability of another.

An engineering workstation must be trusted to produce and transfer authorized applications. The runtime must be trusted to load and execute those applications correctly. The host operating system must provide a sufficiently protected environment for the runtime. Network infrastructure must restrict communication to the required systems and interfaces.

A compromise of one component can therefore affect other components that rely on it.

The software PLC should consequently be assessed as a system of interconnected trust relationships rather than as an isolated runtime process [1].

## 3. Host Operating System and Runtime Boundaries

The host operating system is an important part of the software PLC's trusted computing environment. It provides the services required by the runtime, including process scheduling, memory management, networking, storage, and hardware access.

The strength of the boundary between the runtime and its host depends on the deployment model.

### 3.1 Native Host Deployment

In a native host deployment, the PLC runtime executes as one or more processes within the host operating system. The runtime depends on the host kernel and inherits the security properties of its process permissions, filesystem access, network configuration, and available system resources.

A compromise of the host operating system can undermine the security of the runtime because the host controls the environment in which its processes execute.

### 3.2 Containerized Deployment

Containers provide process and resource isolation through operating-system mechanisms such as namespaces and control groups. However, containers share the host operating system's kernel. They do not provide the same isolation boundary as virtual machines with separate guest kernels.

The container's security therefore depends on several configuration properties:

- Process user and group identities.
- Linux capabilities and privileged mode.
- Filesystem mounts and access permissions.
- Device mappings.
- Network configuration.
- Seccomp and other security restrictions.
- CPU and memory resource controls.
- Access to the container engine and its management interface.

Docker identifies the daemon, container privileges, mounted resources, and kernel attack surface as important security considerations [3].

A container running with excessive privileges or broad access to host resources can weaken the intended isolation between the PLC runtime and the host.

### 3.3 Virtual Machine Deployment

A virtual machine provides a guest operating system and virtual hardware environment managed by a hypervisor.

The hypervisor mediates access to physical resources and establishes a boundary between guest workloads and the underlying host.

The hypervisor and its management interfaces become part of the trusted computing base. Its configuration, virtual networking, device passthrough, resource allocation, and administrative access influence the security of the PLC environment.

A virtual machine can provide stronger separation from other workloads than a conventional container, but this depends on the hypervisor's security and configuration [1].

### 3.4 Host and Runtime Dependencies

Regardless of deployment model, the runtime depends on components outside the control application itself.

These may include:

- Host kernel and operating system services.
- Runtime libraries and shared dependencies.
- Container engine or hypervisor.
- I/O drivers and communication plugins.
- Filesystem and storage services.
- Network interfaces and supporting services.

These dependencies form part of the runtime's trusted computing base. A failure or compromise in one of them can affect application execution, communication, or availability.

## 4. User and Process Privileges

Software PLC environments have operating-system identities and application-level accounts. These serve different purposes and should not be treated as interchangeable.

### 4.1 Operating-System Privileges

Operating-system privileges determine what a process can access or modify on its host.

Depending on its permissions, a process may be able to:

- Read or modify application files.
- Access runtime configuration and credentials.
- Open network sockets.
- Communicate with other processes.
- Access hardware devices.
- Change scheduling parameters.
- Perform privileged system operations.

Processes running with unnecessary privileges increase the potential impact of a compromise. The principle of least privilege requires each process and user to receive only the permissions needed to perform its assigned functions [1].

### 4.2 Application-Level Authorization

Application-level authorization determines which operations an authenticated user can perform through the PLC management interface.

Depending on the runtime, these operations may include:

- Viewing runtime status.
- Monitoring variables.
- Modifying application values.
- Uploading or deploying programs.
- Starting and stopping execution.
- Managing users and configuration.

A user authorized to monitor a controller does not necessarily need permission to deploy a new application or change runtime configuration.

These capabilities should be separated where the platform supports such controls.

### 4.3 Process Separation

A software PLC may separate management, execution, logging, and communication into different processes.

Process separation can improve organization and reduce the responsibilities assigned to individual components. However, it does not automatically establish a security boundary.

Two processes may still share:

- The same operating-system user.
- Similar filesystem permissions.
- Access to the same configuration files.
- Privileged capabilities.
- Shared storage and network resources.

The security significance of process separation depends on the actual identities, permissions, communication mechanisms, and resource access assigned to each process.

### 4.4 OpenPLC Runtime v4

OpenPLC Runtime v4 documents a Python-based management service and a separate C/C++ execution process. The components communicate through Unix domain sockets [7, 8, 9].

The architecture establishes process separation between management and execution responsibilities. It does not, by itself, establish that the processes use different operating-system identities or have independently restricted privileges.

The runtime documentation also describes the use of real-time scheduling through `SCHED_FIFO` and the `CAP_SYS_NICE` capability.

On Linux, real-time scheduling permissions can also be influenced by resource limits such as `RLIMIT_RTPRIO`. The effective privileges therefore depend on the host and container configuration [4, 5].

That matters when evaluating a deployment: a runtime's documented privilege requirements do not establish which privileges were actually granted to its processes.

## 5. Engineering Workstation Trust

The engineering workstation is a privileged component in the software PLC environment because it is used to develop, configure, and deploy control applications.

It may contain engineering software, project files, libraries, credentials, certificates, and application archives. It also provides the tools used to interact with the target runtime.

### 5.1 Engineering Workstation as a Trusted Component

The engineering workflow establishes a trust relationship between the workstation and the PLC runtime:

1. The engineer develops or modifies a PLC project.
2. The engineering environment processes and compiles the project.
3. The resulting application or project package is prepared for transfer.
4. The package is transferred to the target runtime.
5. The runtime validates, loads, and executes the application.

The engineering workstation is therefore part of the application's trusted development and deployment chain.

If an attacker compromises the workstation or modifies an engineering project, the resulting application may be transferred through otherwise legitimate engineering operations.

MITRE ATT&CK for ICS describes this behavior through Project File Infection (T0873), which covers modification of project files that can subsequently be transferred to controllers [10].

### 5.2 Engineering Access and Authorization

Engineering access should be treated as privileged operational access.

The ability to connect to a runtime should not automatically grant every available engineering capability.

Relevant access distinctions include:

- Monitoring and diagnostic access.
- Application modification.
- Program upload and download.
- Runtime operation and configuration.
- User and credential management.

Access should be restricted according to operational responsibilities, using least privilege and role-based authorization where supported [1].

### 5.3 Engineering Project Protection

Engineering projects should be protected throughout their lifecycle.

Relevant controls include:

- Restricting access to project files and repositories.
- Managing engineering workstation accounts.
- Protecting stored credentials and certificates.
- Reviewing project changes before deployment.
- Maintaining version history.
- Verifying project and build artifacts.
- Restricting access to controller programming interfaces.

Project archives and backups should also be protected because they may contain control logic, device configuration, and other information useful to an attacker.

## 6. Application and Program Integrity

Application integrity concerns whether the PLC executes the intended and authorized control application.

A PLC application passes through several stages before execution:

```text
Engineering Project
        |
        v
Compilation and Build
        |
        v
Program Package
        |
        v
Transfer to Runtime
        |
        v
Application Loading
        |
        v
Execution
```

Each stage introduces a trust relationship. An application can be modified before compilation, during storage, before transfer, or after deployment.

### 6.1 Integrity Across the Application Lifecycle

Integrity controls should cover the complete application lifecycle rather than only the program transfer operation.

Relevant controls include:

- Protected engineering project repositories.
- Controlled access to compilation and deployment tools.
- Cryptographic hashes for identifying changes to files and build artifacts.
- Digital signatures for verifying application authenticity.
- Authenticated and protected program transfer.
- Comparison between approved project revisions and deployed applications.
- Audit records of application downloads and modifications.

A cryptographic hash can establish whether a file matches a known reference. It does not independently prove who created or authorized the file.

Digital signatures can provide authenticity when the signing keys and verification process are properly protected.

NIST SP 1800-10 provides practical examples of protecting information and system integrity in industrial control environments, including detecting unauthorized PLC logic modifications and protecting system configurations [14].

### 6.2 Upload Validation and Application Authenticity

An application upload mechanism may validate the structure and contents of an uploaded package before extracting or processing it.

These checks can protect against malformed archives, path traversal, excessive file sizes, and other unsafe upload conditions.

However, successful validation does not prove that the application is trusted or authorized. An archive containing malicious or unauthorized control logic may still be structurally valid.

Upload validation and application integrity therefore address different security requirements.

### 6.3 OpenPLC Runtime v4.3.1

The OpenPLC Runtime v4.3.1 security documentation describes several protections for uploaded project archives, including:

- ZIP path traversal validation.
- File size restrictions.
- Compression-ratio checks.
- File extension restrictions.
- Safe extraction operations.

These protections reduce risks associated with processing uploaded archives. They do not establish the authenticity of the PLC application [7].

The same documentation describes the stored source project as an unencrypted ZIP archive without a signature or checksum integrity guarantee. Filesystem access can therefore expose the stored project, and modifications to the archive are not independently detected through a documented signature or checksum mechanism [7].

This illustrates the difference between validating an upload and maintaining application integrity after deployment.

These are documented properties of the v4.3.1 release, not findings from an independent test of every possible deployment configuration.

## 7. Network and Management Interfaces

Software PLCs expose interfaces for engineering, management, diagnostics, and industrial communication.

These interfaces create communication paths through which external systems can access or influence the runtime.

### 7.1 Management Interfaces

Management interfaces may provide functions such as:

- User authentication.
- Program upload and deployment.
- Runtime start and stop operations.
- Status and diagnostic retrieval.
- Variable monitoring and modification.
- Debugging and configuration management.

These operations can directly affect the application or runtime and should be protected accordingly.

OpenPLC Runtime v4.3.1 documents an HTTPS REST API for communication with OpenPLC Editor, along with JWT authentication for protected API operations and a WebSocket debugging interface [8].

The use of HTTPS and JWT does not independently establish that every interface is secure. Certificate validation, credential protection, authorization, session handling, and network exposure remain relevant.

### 7.2 Initial Account Creation

The v4.3.1 API documentation describes an initial account-creation operation through `POST /api/create-user`. This operation is available before an initial user account has been established. Subsequent account creation and protected operations require authentication [8]. This is an initial setup condition rather than evidence of an authentication vulnerability by itself.

The security of the bootstrap process depends on how the runtime is deployed and whether initial account creation is performed in a controlled environment before exposing management access to other networks.

### 7.3 TLS Certificate Validation

The v4.3.1 documentation describes the use of self-signed TLS certificates by default.

Its client examples include options such as `curl -k` and Python's `verify=False`, which disable certificate verification [7, 8].

HTTPS provides an encrypted communication channel, but a client that does not verify the server certificate may not reliably establish the server's identity.

A production deployment should use an appropriate certificate-management process and ensure that clients validate the certificate presented by the runtime.

### 7.4 Industrial Communication Interfaces

A software PLC may expose industrial protocols through its runtime, drivers, or communication plugins.

Depending on the implementation and configuration, these may include:

- Modbus TCP.
- OPC UA.
- EtherNet/IP.
- PROFINET.
- Serial and other fieldbus interfaces.

These interfaces may support communication with HMIs, engineering tools, remote I/O, drives, sensors, and other controllers. Their security properties depend on the protocol, implementation, authentication mechanisms, network placement, and configuration.

An interface used for process data exchange should not automatically be treated as an interface suitable for remote management.

### 7.5 Network Placement and Isolation

The network architecture determines which systems can communicate with the PLC runtime and its supporting services.

Relevant boundaries include:

- Enterprise network to OT network.
- Engineering workstation to runtime.
- Management network to runtime services.
- Runtime to field devices.
- Container network to host and external networks.
- Remote access infrastructure to engineering services.

NIST recommends segmenting OT networks according to operational requirements and restricting communication to authorized paths. Firewalls, gateways, and other isolation mechanisms can enforce these boundaries [1].

### 7.6 OpenPLC UDP Discovery

The OpenPLC Runtime v4.3.1 security documentation describes a UDP discovery service on port 33333.

The discovery response can disclose metadata such as the stored project name and timestamp without authentication. The documentation states that the project archive itself is not served through this discovery mechanism [7].

This is a metadata exposure to systems that can reach the discovery service. It should not be interpreted as a mechanism for downloading PLC source code.

## 8. Runtime Availability

Software PLC availability depends on the continued operation of the runtime and the components supporting it.

A failure in the host operating system, container engine, hypervisor, runtime process, I/O driver, network, or storage system can interrupt control application execution.

### 8.1 Resource Availability

Software PLCs use host resources such as:

- CPU processing time.
- Memory.
- Storage capacity.
- Network bandwidth.
- Hardware and I/O access.

Resource exhaustion or excessive workload can affect execution timing, communications, and runtime responsiveness.

Relevant conditions include:

- CPU contention with unrelated workloads.
- Memory exhaustion.
- Storage exhaustion or failure.
- Excessive network traffic.
- Runtime process crashes.
- Failed I/O drivers.
- Scheduling delays.
- Host or container termination.

Resource allocation and isolation are therefore part of the security architecture.

### 8.2 Component Availability

Separating management and execution processes can help organize runtime responsibilities, but it does not guarantee independent availability. A management service may fail while execution continues, or a failure in a shared dependency may affect both components.

Similarly, a container restart or host failure can interrupt multiple services hosted within the same environment. Availability must therefore be evaluated across the complete dependency chain.

### 8.3 OT Availability Requirements

NIST identifies availability as a particularly important security objective in OT environments because system interruptions can affect physical processes and operational continuity [1].

For software PLCs, availability planning should consider the host, runtime, network, storage, I/O infrastructure, recovery procedures, and supporting services.

## 9. Component Dependencies and Trust Relationships

The following table summarizes the principal components and their security relevance.

| Component | Trust relationship | Security concern |
|---|---|---|
| Physical hardware | Provides computing and I/O resources | Physical access, hardware failure, firmware integrity |
| Host firmware | Initializes and manages hardware | Unauthorized configuration or firmware modification |
| Operating system and kernel | Provides process, memory, networking, and device services | Vulnerabilities, privilege escalation, host compromise |
| Hypervisor or container engine | Provides workload isolation | Misconfiguration, excessive privileges, isolation failure |
| PLC runtime | Loads and executes the control application | Runtime compromise, unauthorized control, execution failure |
| Engineering environment | Creates and transfers applications | Compromised workstation, malicious project files |
| Application and libraries | Define control behavior | Unauthorized modification and vulnerable dependencies |
| I/O drivers and plugins | Connect runtime to external devices | Driver compromise and incorrect I/O behavior |
| Management interfaces | Allow users and tools to manage the runtime | Unauthorized access and configuration changes |
| Network infrastructure | Connects engineering, runtime, and field devices | Unauthorized connectivity, interception, disruption |
| Storage and backups | Preserve projects, configuration, and runtime data | Exposure, tampering, corruption, recovery failure |
| Credentials and certificates | Establish identity and access | Credential theft, weak authentication, key exposure |

These components form a chain of trust. A weakness in one component can undermine the security of components that depend on it.

For example:

- A compromised engineering workstation can affect application integrity.
- A compromised host operating system can undermine container isolation.
- A compromised management service can expose application deployment functions.
- A modified I/O driver can influence communication between the runtime and the industrial process.
- A failed host can interrupt every PLC runtime hosted on it.

This dependency model is conceptual. The exact components and relationships vary between software PLC products and deployment configurations.

## 10. Consolidated Attack Surface

The attack surface includes the interfaces, services, components, and operational paths through which a software PLC environment can be accessed or influenced.

The following table consolidates the principal areas identified in this investigation.

| Attack-surface area | Relevant entry point or component | Potential security impact |
|---|---|---|
| Host environment | OS services, kernel, host accounts | Host compromise and loss of runtime isolation |
| Container or VM | Management interfaces, privileges, virtual devices | Isolation failure and resource interference |
| User and process privileges | OS accounts, capabilities, process permissions | Unauthorized access to runtime resources |
| Engineering workstation | IDE, project files, libraries, credentials | Application compromise and unauthorized deployment |
| Application integrity | Source code, build artifacts, program packages | Unauthorized control logic or configuration |
| Management interfaces | REST APIs, WebSockets, engineering connections | Unauthorized monitoring, modification, or control |
| Industrial protocols | Runtime protocol services and I/O interfaces | Unauthorized commands, data manipulation, disruption |
| Network infrastructure | Remote access, routing, switching, firewalls | Unauthorized connectivity, interception, denial of service |
| Runtime dependencies | Drivers, plugins, libraries, databases | Execution compromise and unexpected behavior |
| Storage | Project archives, configuration files, secrets | Data exposure, tampering, recovery failure |
| Availability dependencies | CPU, memory, storage, power, host services | Runtime interruption and process disruption |

### 10.1 Relevant MITRE ATT&CK for ICS Techniques

MITRE ATT&CK for ICS provides examples of adversary behavior relevant to software PLC environments.

| Technique | ID | Security relevance |
|---|---|---|
| Program Download: Download All | T0843.001 | Replacement of PLC logic and configuration |
| Program Download: Online Edit | T0843.002 | Modification of a running control application |
| Program Download: Program Append | T0843.003 | Addition of program logic to an existing application |
| Program Upload | T0845 | Collection of application logic and process information |
| Project File Infection | T0873 | Modification of engineering project files before deployment |
| Adversary-in-the-Middle | T0830 | Interception or modification of communications |

These techniques describe possible adversary behaviors, not evidence that a particular software PLC implementation is vulnerable to each technique [10, 11, 12, 13].

Relevant defensive measures include access management, authorization enforcement, application integrity verification, protected engineering workstations, network filtering, segmentation, and audit logging [1, 14].


## 12. Technical Assessment

Software PLC security depends on the relationships between the host environment, runtime, engineering workstation, control application, management interfaces, and industrial network.

The host operating system and isolation mechanism establish the environment in which the runtime operates. Process and user privileges determine what individual components can access. The engineering workstation and its project files form part of the trusted development and deployment chain.

Application integrity must be maintained from project development through compilation, transfer, loading, and execution. Network and management interfaces require controlled access because they expose functions capable of influencing the runtime and application.

Availability depends on the continued operation of the host, runtime, network, storage, I/O infrastructure, and supporting components.

The resulting security architecture is distributed across multiple trust boundaries. Protecting only the PLC runtime does not adequately protect the complete software PLC environment.

This investigation establishes the security architecture and consolidated attack surface that provide the baseline for further practical software PLC security investigations.
