# Physical PLCs vs. Software PLCs

**Research Area:** Software PLC Foundations  
**Investigation:** 01  
**Document Type:** Technical Research Report  
**Research Focus:** Architecture, implementation, execution environments, and security implications

---

## 1. Scope and Context

Programmable Logic Controllers (PLCs) are industrial computing systems designed to execute control applications and interact with physical processes. Traditionally, these systems have been implemented using dedicated controller hardware, with integrated firmware, processing resources, and industrial I/O interfaces.

Software PLCs (SoftPLCs) implement equivalent control functionality through software runtimes operating on compatible computing platforms. This changes how controller functionality is deployed and managed without changing the fundamental purpose of a PLC.

This investigation examines the architectural differences between traditional hardware PLCs and software PLC implementations. It considers their hardware and software responsibilities, execution environments, operational characteristics, and associated security implications.

The comparison focuses on general architectural principles rather than specific product capabilities. Siemens SIMATIC S7-1500 hardware and Software Controller implementations, CODESYS Control, and OpenPLC Runtime are used as implementation references where appropriate.

### 1.1 Terminology

| Term                    |                   Description                                                                             |
|-------------------------|-----------------------------------------------------------------------------------------------------------|
| Hardware PLC            | A programmable controller implemented on a dedicated industrial controller platform.                      |
| Software PLC (SoftPLC)  | A software runtime that executes PLC applications on a compatible computing platform.                     |
| PLC Runtime             | The execution environment responsible for loading and executing PLC applications.                         |
| Firmware                | Low-level software responsible for initializing and managing hardware and providing system functionality. |
| Control Application     | The user-developed program defining the behavior of an industrial process.                                |
| I/O Modules             | Hardware interfaces used to acquire process inputs and control physical outputs.                          |
| Engineering Environment | Software used to develop, configure, compile, deploy, and monitor PLC applications.                       |

The term *physical PLC* is used in this document to distinguish dedicated controller hardware from software-based PLC implementations. It does not imply that software PLCs operate without physical hardware. The term *SoftPLC* is used in technical literature, although its precise definition is not universally standardized [4].

## 2. Traditional PLC Architecture

A traditional PLC is an industrial computing system built around a dedicated controller platform. Its hardware, system software, and interfaces are designed to support industrial control operations.

Depending on the product, the controller may use an integrated or modular architecture. Modular implementations commonly separate processing, power, communication, and I/O functions into individual components.

### 2.1 Controller Components

| Component                     | Technical Responsibility                                                               |
|-------------------------------|----------------------------------------------------------------------------------------|
| Power Supply                  | Provides operating power to the controller and associated modules.                     |
| Central Processing Unit (CPU) | Executes the control application and manages controller operations.                    |
| Memory                        | Stores the user program, system data, and process data.                                |
| Input Modules                 | Acquire signals from connected sensors and other field devices.                        |
| Output Modules                | Deliver control signals to actuators and other field devices.                          |
| Backplane                     | Provides internal communication between controller modules.                            |
| Communication Modules         | Provide interfaces to engineering systems, other controllers, and industrial networks. |

Not all PLCs use this exact arrangement. Compact controllers may integrate several components into a single unit, while modular systems allow individual components to be installed or replaced.

### 2.2 Hardware and Software Responsibilities

A traditional PLC combines physical computing components with software responsible for managing controller operations.

**1. Hardware layer**

Includes the CPU, memory, power supply, communication interfaces, and physical I/O components.

**2. Firmware and system software layer**

Provides hardware initialization, system management, diagnostic functionality, and the execution environment required by the control application. Depending on the controller, this may include an embedded operating system or real-time operating system (RTOS).

**3. Application layer**

Contains the user-developed control logic. The application defines how acquired process information is evaluated and how outputs are controlled.

These layers have distinct responsibilities, even when they are tightly integrated within a manufacturer's controller platform [1].

### 2.4 Implementation Reference: Siemens SIMATIC S7-1500

The Siemens SIMATIC S7-1500 illustrates a modular hardware PLC implementation. Its product family includes CPUs, power supply modules, signal modules, technology modules, and communication modules [7].

The CPU provides the primary control execution capability, while the associated modules provide physical and communication interfaces.

This implementation demonstrates how PLC functionality can be delivered through a dedicated controller platform with manufacturer-defined hardware and system software. It is an example of this architecture, rather than a representation of every PLC implementation.

## 3. Software PLC Architecture

A software PLC implements PLC functionality through a runtime environment executing on a compatible computing platform.

Instead of relying on a single dedicated controller architecture, the PLC runtime can operate on different computing platforms, provided that the hardware, execution environment, and interfaces meet the runtime's requirements.

Potential deployment platforms include:

- Industrial PCs.
- Embedded computing devices.
- General-purpose computers.
- ARM- and x86-based systems.
- Virtualized computing environments.

The central architectural component is the PLC runtime, which provides the environment for loading and executing control applications [4][8].

### 3.1 Runtime Architecture

A software PLC environment generally consists of several interacting components.

| Component             | Technical Responsibility                                                            |
|-----------------------|-------------------------------------------------------------------------------------|
| Host Hardware         | Provides processing resources, memory, storage, and physical interfaces.            |
| Host Firmware         | Initializes and manages the underlying computing hardware.                          |
| Operating Environment | Provides process management, memory management, device access, and system services. |
| PLC Runtime           | Provides the execution environment for PLC applications.                            |
| Execution Engine      | Performs the execution of compiled or interpreted control logic.                    |
| I/O Drivers           | Provide access to local or remote industrial I/O interfaces.                        |
| Management Interfaces | Support configuration, program transfer, monitoring, and runtime management.        |

The exact component arrangement depends on the implementation. Some runtimes combine several responsibilities, while others separate management services and control execution into independent processes. Some virtualized implementations also use a hypervisor to isolate controller execution and allocate hardware resources independently of a general-purpose host operating system [8].

### 3.2 Host and Runtime Relationship

A software PLC separates PLC-specific functionality from the underlying computing platform. The host provides physical resources and, depending on the deployment model, system services required by the runtime.

The runtime manages control application execution and interaction with supported I/O interfaces. Its relationship with the host depends on the implementation. A runtime may operate as a process under a host operating system, use a real-time execution environment, or run within a virtualized environment with resources reserved for controller operation [8].

Consequently, host operating systems, drivers, libraries, and supporting services may form part of the software PLC's dependency chain. The extent of these dependencies depends on the runtime architecture and deployment configuration.

*Figure 2: Simplified software PLC architecture.*

The illustration represents one possible logical software stack. It does not represent every deployment model. A hypervisor-based implementation may isolate the PLC execution environment and reserve processor, memory, or I/O resources rather than relying on the same host operating system shown here [8].

### 3.4 Implementation Reference: CODESYS Control

CODESYS Control provides an example of a software-based PLC runtime.

Its runtime implementations support compatible industrial computing platforms. CODESYS also offers virtual PLC products, demonstrating how PLC runtime instances can be deployed in virtualized computing environments [9].

This illustrates the separation between PLC runtime functionality and the underlying computing platform, while also showing that software PLC deployment does not require a single fixed host architecture.

### 3.5 Implementation Reference: Siemens SIMATIC S7-1500 Software Controller

Siemens also provides a software controller implementation within the SIMATIC S7-1500 family.

The S7-1500 Software Controller is designed for PC-based deployment. Its documented architecture uses a real-time environment and a hypervisor-based approach to separate controller execution from Windows. Hardware resources can be reserved for the software controller, limiting access from the Windows environment to those resources [8].

This is an important architectural example because it demonstrates that a software PLC does not necessarily execute as an ordinary application sharing all resources with the host operating system.

### 3.6 Implementation Reference: OpenPLC Runtime v4

OpenPLC Runtime v4 provides an open-source reference implementation for examining software PLC architecture.

The v4.3.1 implementation used as the reference for this research separates runtime management functionality from control execution [10].

Its documented architecture includes:

| Component        | Responsibility                                                                                    |
|------------------|---------------------------------------------------------------------------------------------------|
| REST API Server  | Handles management operations, engineering communication, program uploads, and execution control. |
| PLC Runtime Core | Executes the loaded control application.                                                          |
| I/O Plugins      | Provide integration with supported hardware and communication interfaces.                         |

The implementation uses a Python-based management service alongside a C/C++ execution environment. This separation illustrates an important architectural distinction: the interfaces used to manage a PLC do not necessarily belong to the component responsible for executing its control application.

## 4. Architectural Comparison

Both traditional hardware PLCs and software PLCs perform industrial control functions. Their primary distinction is the implementation and organization of the computing environment responsible for those functions.

### 4.1 Hardware and Software Responsibilities

| Responsibility | Traditional PLC | Software PLC |
|---|---|---|
| Computing Hardware | Dedicated controller platform | Compatible industrial or general-purpose computing platform |
| System Firmware | Controller-specific firmware | Host platform firmware and, where applicable, platform-specific firmware |
| Operating Environment | Embedded system, RTOS, or other controller environment | Host OS, RTOS, hypervisor-based environment, or another supported execution environment |
| PLC Runtime | Integrated into the controller platform | Installed or deployed as software |
| Control Application | Stored and executed by the controller | Loaded and executed by the PLC runtime |
| I/O Integration | Integrated, modular, or remote I/O | Local interfaces, supported drivers, fieldbus, or remote I/O |
| Management Interfaces | Controller-specific services and interfaces | Runtime APIs, management services, and engineering interfaces |

The software PLC does not eliminate the hardware layer. It changes the relationship between the PLC-specific software and the underlying computing platform.

### 4.2 Architectural Characteristics

| Characteristic | Traditional PLC | Software PLC |
|---|---|---|
| Platform Dependency | Controller-specific hardware and firmware | Compatible host hardware and runtime environment |
| Hardware Flexibility | Generally tied to a controller family | Can support multiple compatible computing platforms |
| System Integration | Often centered around the controller ecosystem | Can integrate with other software and host services |
| Resource Allocation | Managed by the controller platform | Depends on the runtime and deployment architecture |
| Software Dependencies | Firmware and controller-specific components | Runtime and supporting dependencies; may also include host OS, drivers, libraries, and services |
| I/O Expansion | Additional modules or supported remote I/O | Additional interfaces, drivers, or supported remote I/O |

These characteristics describe common implementation patterns. They are not absolute limitations of either architecture. In particular, a software PLC using dedicated or hypervisor-reserved resources may have a substantially different resource and isolation model from one running as an ordinary host process [8].

### 4.3 Architectural Dependency

The dependency relationship can be summarized as follows:

**Traditional hardware PLC**

```text

        |
Controller Firmware / System Software
        |
PLC Execution Environment
        |

        |

```

**Software PLC: general host-based deployment**

```text

        |
Host Firmware
        |
Operating Environment
        |

        |

        |

```

**Software PLC: isolated or virtualized deployment**

```text

        |

        |

        |

        |

        |

```

These representations show different deployment arrangements rather than mandatory layers shared by every implementation. The software PLC's dependencies and isolation boundaries must be evaluated against its actual architecture.

## 5. Operational Characteristics

The architectural differences influence how each implementation is deployed, maintained, integrated, and operated.

### 5.1 Hardware and Resource Requirements

Traditional PLCs generally use controller-specific processing and memory resources. Their capabilities are determined by the selected controller model and supported expansion components.

Software PLCs use the resources of their host computing platform. Depending on the implementation, this can provide flexibility in processor selection, memory allocation, storage, and software integration.

However, deployments that share computing resources with other workloads introduce additional considerations. Competing workloads, processor contention, and memory pressure may affect control execution and system availability. Isolated or resource-reserved deployments can reduce some of these interactions, but their effectiveness depends on the underlying configuration.

### 5.2 Environmental Suitability

Industrial environments impose requirements beyond basic computing functionality.

Relevant considerations include:

- Operating temperature and humidity.
- Electromagnetic compatibility.
- Mechanical vibration and shock.
- Power supply characteristics.
- Electrical isolation.
- Industrial communication interfaces.

Dedicated industrial PLCs are generally designed and qualified for specified operating environments.

A software PLC running on an industrial PC can also be suitable for industrial deployment, provided that the complete equipment and associated interfaces meet the requirements of the intended application.

An ordinary desktop computer running PLC software should not automatically be considered equivalent to industrial-rated controller equipment.

IEC 61131-2:2017 specifies functional and electromagnetic compatibility requirements and verification tests for programmable controller equipment and associated peripherals whose primary purpose is industrial control [2]. The applicability of these requirements should be evaluated against the intended equipment and its declared use, rather than assuming that every computer running PLC software is automatically covered.

### 5.3 Integration and Maintenance

Traditional PLCs are commonly maintained through controller-specific engineering environments, firmware updates, hardware replacement, and manufacturer-supported expansion components.

Software PLCs introduce additional maintenance responsibilities involving the host platform, runtime software, supporting libraries, drivers, and computing hardware. The exact maintenance scope depends on the deployment model and the degree of separation between the host and controller execution environments.

The separation between host and runtime can provide flexibility, but it also requires compatibility and lifecycle management across the relevant hardware and software components.

## 6. Execution Environment and Timing

The execution environment determines how control applications are scheduled and executed. This is an important consideration when comparing dedicated controller platforms with software-based implementations.

### 6.1 Traditional PLC Execution Environment

Traditional PLCs commonly operate within controller-specific execution environments.

Depending on the implementation, these may include:

- Embedded system software.
- Real-time operating systems.
- Controller-managed execution tasks.
- Dedicated processor resources.
- Hardware-specific I/O handling.
- Watchdog and diagnostic mechanisms.

Some controllers execute control applications without a conventional operating system. Others use an RTOS or proprietary system environment [1][4].

### 6.2 Software PLC Execution Environment

Software PLCs rely on the execution capabilities of their host platform and runtime.

Depending on the implementation, the environment may include:

- General-purpose operating systems.
- Real-time operating systems.
- Real-time kernel extensions.
- Hypervisors.
- Hardware-specific drivers.
- Runtime-managed task scheduling.

The relationship between the operating environment and runtime varies. In some deployments, the host OS coordinates processor access and other resources. In others, a real-time environment or hypervisor provides a separate execution context for the controller [8].

### 6.3 Deterministic Execution

Deterministic execution is important in industrial control because applications often operate under defined timing requirements.

A common misconception is that dedicated hardware PLCs are inherently deterministic while software PLCs cannot provide deterministic execution.

In practice, execution timing depends on the complete system configuration, including:

- Processor architecture and performance.
- Task scheduling mechanisms.
- Operating environment behavior.
- Runtime implementation.
- I/O handling.
- Resource contention.
- Communication and network delays.

Software PLC implementations can employ real-time scheduling mechanisms, suitable computing platforms, and resource isolation to achieve predictable execution behavior.

Research published at IEEE ETFA 2022, *How Real (Time) Are Virtual PLCs?*, evaluated virtual PLC implementations and reported comparable timing behavior to a non-virtualized software PLC for the tested configurations and workloads [5].

These findings demonstrate that virtualization does not automatically prevent deterministic execution. They do not establish that every virtualized PLC configuration can satisfy every industrial timing requirement.

The relevant consideration is whether the complete implementation meets the timing requirements of its intended control application.

## 7. Security Implications

The architectural differences influence the components, dependencies, and interfaces that must be considered when assessing PLC security.

Neither implementation should be assumed to be inherently secure based solely on its hardware or software classification. Security depends on the implementation, configuration, exposed interfaces, and operational environment [4][11].

### 7.1 Platform Dependencies

Traditional PLCs depend on controller firmware, embedded system software, runtime components, and supported communication interfaces.

Software PLCs may introduce dependencies on the host platform, including its firmware, operating system, drivers, libraries, and runtime components. The specific dependencies depend on whether the controller executes as a host process, within a real-time environment, or in an isolated virtualized configuration.

A compromise of a software PLC's host environment may affect the availability or integrity of the PLC runtime and its control application. However, the extent of this impact depends on process privileges, isolation mechanisms, resource separation, and system configuration.

### 7.2 Runtime and Application Integrity

Both architectures depend on the integrity of the PLC runtime and the control application.

Unauthorized modification of control logic can alter the behavior of an industrial process regardless of whether the application executes on dedicated controller hardware or a general-purpose computing platform.

Software PLC implementations may also expose management interfaces for application deployment, configuration, monitoring, and execution control.

These interfaces require appropriate authentication, authorization, and access restrictions. The security of engineering and management paths is relevant to both hardware and software PLC deployments [4][11].

### 7.3 Privileges and Isolation

A traditional PLC generally operates within a controller-specific privilege and access model.

Software PLCs can introduce additional security considerations associated with their host operating environment. These may include:

- Process execution privileges.
- User and service accounts.
- File-system permissions.
- Inter-process communication.
- Network service exposure.
- Isolation from other host processes.

Insufficient isolation or excessive runtime privileges can increase the potential impact of a host compromise. However, these risks vary with the deployment model. A hypervisor-based software controller with reserved resources has a different trust boundary from a runtime operating as an ordinary process under a general-purpose OS [8].

### 7.4 Availability and Resource Contention

Traditional PLCs generally use controller-managed computing resources.

Software PLCs may share host resources with other processes and services, depending on their deployment configuration. Resource exhaustion, process interference, or failures in supporting host services may affect runtime availability and execution timing.

Resource reservation and isolation can reduce some forms of interference, but they do not eliminate all availability risks. Host hardware, platform firmware, runtime dependencies, I/O interfaces, and external infrastructure remain relevant to the overall system.

### 7.5 Comparative Security Considerations

| Security Area | Traditional PLC | Software PLC |
|---|---|---|
| Platform Integrity | Controller firmware and embedded system integrity | Host firmware and platform integrity, including the OS or hypervisor where applicable |
| Runtime Integrity | Controller-specific execution environment | PLC runtime and supporting dependencies |
| Application Integrity | Control program storage and modification mechanisms | Control program storage, deployment, and runtime loading |
| Privilege Management | Controller-specific access controls | Host operating system privileges and runtime permissions, where applicable |
| Interface Exposure | Controller communication and engineering interfaces | Runtime APIs, management services, host services, and communication interfaces |
| Availability | Controller hardware, firmware, and execution resources | Host hardware, platform environment, runtime, and shared resources where applicable |
| Isolation | Controller-specific hardware and software mechanisms | Process, OS, container, or virtualization isolation mechanisms |

The table identifies architectural security considerations rather than confirmed vulnerabilities.

A complete security assessment must consider the implementation, configuration, network placement, engineering environment, and operational requirements of the deployed system. This is consistent with the broader OT security approach described in NIST SP 800-82 Rev. 3 [11].

## 8. Technical Assessment

Traditional hardware PLCs and software PLCs implement the same fundamental industrial control responsibility through different computing architectures.

Traditional PLCs integrate processing hardware, system software, execution environments, and industrial interfaces into dedicated controller platforms.

Software PLCs separate PLC-specific functionality into a runtime that operates on a compatible computing platform. This introduces flexibility in hardware selection and software integration while creating dependencies that vary with the host and deployment architecture.

The difference is particularly relevant in three areas:

**Architecture:** Traditional PLCs generally provide an integrated controller platform, whereas software PLCs implement controller functionality through a runtime deployed on a compatible computing platform. The runtime may operate under a host OS or within a separately isolated execution environment.

**Operations:** Software PLCs can offer flexibility in computing resources and deployment, but their suitability depends on hardware qualification, runtime compatibility, I/O integration, and execution requirements.

**Security:** Software PLCs can introduce additional platform dependencies involving the host operating system, runtime components, drivers, and supporting services. The extent of these dependencies depends on the deployment model. Traditional PLCs retain their own firmware, runtime, communication, and engineering security requirements.

Neither architecture is universally superior. Their suitability depends on the control application, operational environment, performance requirements, integration needs, and security constraints.

The architectural distinctions established here provide the basis for examining software PLC deployment models, where the choice of host environment and deployment arrangement introduces further operational and security considerations.
