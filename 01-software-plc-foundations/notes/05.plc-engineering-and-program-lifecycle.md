# PLC Engineering and Program Lifecycle

**Research Area:** Software PLC Foundations
**Investigation:** 05
**Document Type:** Technical Research Report
**Research Focus:** PLC applications development, compilation, transferring, deployement, modification, and maintainance.

---

## 1. Scope and Context

PLC applications go through an engineering and deployment lifecycle before and after they execute on a controller. This lifecycle includes project development, hardware and software configuration, compilation, program transfer, online monitoring, modification, version management, and recovery.

The engineering environment provides the tools used to develop and manage the application. The PLC runtime receives the application and provides the environment in which it executes.

These are separate but connected environments. Changes made to an offline engineering project do not automatically change the application running on a controller. Similarly, modifications made directly to a running application may not be reflected in the engineering project saved on the workstation.

This investigation examines how PLC applications move between these environments and how their state is maintained throughout their operational lifecycle.

Siemens TIA Portal, CODESYS, and OpenPLC are used as practical examples of engineering and deployment workflows. The objective is to understand the general lifecycle while identifying platform-specific behavior where necessary.

## 2. PLC Engineering Environments

A PLC engineering environment is the software toolchain used to develop, configure, test, and maintain PLC applications.

Depending on the platform, it can provide:

- Editors for IEC 61131-3 programming languages.
- Hardware and device configuration.
- Variable and data type management.
- I/O addressing and mapping.
- Task and execution configuration.
- Library and dependency management.
- Compilation and application validation.
- Program transfer and deployment.
- Online monitoring and diagnostics.
- Project comparison and version management.

Examples include Siemens TIA Portal and CODESYS Development System.

### 2.1 Engineering Project Structure

An engineering project generally contains more than the control logic itself. It can include the application source, controller configuration, device definitions, I/O mappings, task settings, libraries, and communication parameters.

A simplified project structure is:

```text
PLC Engineering Project
│
├── Device Configuration
│   ├── Controller
│   ├── I/O Modules
│   └── Communication Interfaces
│
├── Application
│   ├── Programs
│   ├── Function Blocks
│   ├── Functions
│   ├── Variables and Data Types
│   └── Task Configuration
│
├── Libraries and Dependencies
│
└── Project Settings
```

The actual organization differs between engineering environments. Some platforms organize projects around devices and applications, while others use different object hierarchies.

The engineering project provides the information needed to develop and configure the application for a target controller.

### 2.2 Engineering Environment and Target Compatibility

The engineering environment must support the target controller and its runtime.

Compatibility can depend on:

- Controller model and hardware configuration.
- Firmware and runtime version.
- Engineering software version.
- Supported programming language features.
- Installed libraries and device descriptions.
- Vendor-specific extensions and configuration options.

A project that opens successfully in an engineering environment is not necessarily ready to deploy to every PLC. It must be compatible with the target platform and its available resources.

## 3. Project Development and Compilation

Project development involves creating the control application and configuring the target environment in which it will execute.

### 3.1 Application Development

The engineer creates the application using the programming languages and application organization mechanisms supported by the engineering environment.

This can involve:

1. Creating the PLC project and selecting the target device.
2. Configuring hardware and communication interfaces.
3. Defining variables, data types, and I/O addresses.
4. Developing programs, functions, and function blocks.
5. Configuring tasks and program execution.
6. Adding required libraries and dependencies.
7. Performing application validation and testing.

The engineering environment maintains the relationship between the application logic and its target configuration.

### 3.2 Compilation

Compilation transforms the application into a form that can be loaded and executed by the target runtime.

Depending on the platform, this may involve:

- Syntax and semantic validation.
- Resolving data types and symbol references.
- Resolving library dependencies.
- Generating intermediate representations.
- Generating executable code.
- Linking application components.
- Producing diagnostic and compilation information.

The location of compilation varies. Some engineering environments generate the executable before transfer, while other software PLC architectures perform additional compilation or linking on the target runtime.

A successful compilation indicates that the application passed the checks performed by the toolchain. It does not, by itself, establish that the application behaves correctly on the physical process.

### 3.3 Siemens TIA Portal Example

TIA Portal uses the engineering project to generate project data for the configured automation devices.

Siemens documents that the first download transfers the project data required by the connected device. Subsequent downloads can transfer only the changed project data. The available download operations include hardware and software changes, hardware configuration, changed software objects, and all software objects [1].

The contents and effects of a download therefore depend on the selected operation.

For example, the TIA Portal option **Software (all)** transfers all PLC blocks, PLC data types, and PLC tags. Siemens explicitly documents that this operation resets values to their initial values, including retentive values. This behavior is important when considering the operational impact of deploying a new application.

### 3.4 OpenPLC Runtime v4 Example

OpenPLC Runtime v4 documents a compilation workflow involving both the OpenPLC Editor and the target runtime [2].

The documented process includes:

1. Developing the application in OpenPLC Editor v4.
2. Compiling the project locally into intermediate representations.
3. Packaging the application files into an upload archive.
4. Transferring the archive to the runtime through its management interface.
5. Validating and compiling the uploaded application.
6. Loading the resulting executable into the runtime.

This illustrates a distributed compilation workflow in which the engineering environment prepares the application while the runtime performs additional target-side processing.

The exact generated files and compilation stages are implementation-specific.

## 4. Program Transfer and Deployment

After development and compilation, the application must be transferred to the target controller. Deployment makes the application available to the runtime and prepares it for execution.

### 4.1 Program Transfer

Program transfer generally involves establishing a connection between the engineering workstation and the target controller, selecting the application or project data to transfer, and initiating the download.

The transferred data may include:

- Compiled application code.
- Program blocks and data.
- Hardware configuration.
- I/O configuration.
- Task settings.
- Libraries or other required resources.
- Additional runtime-specific application data.

The exact transfer contents depend on the platform and deployment operation.

### 4.2 Download and Upload

The terms download and upload describe opposite transfer directions.

| Operation | Direction | Purpose |
|---|---|---|
| Download | Engineering environment to PLC | Transfer application or configuration data to the controller. |
| Upload | PLC to engineering environment | Retrieve available application or configuration data from the controller. |

A download can replace or update the application running on the controller.

An upload retrieves information available from the target. The amount of information that can be recovered depends on the controller and engineering environment.

For example, TIA Portal supports uploading hardware configuration and software data from compatible connected devices. However, the available project data and compatibility requirements depend on the target and installed engineering products [3].

An upload should not automatically be treated as a complete recovery of the original engineering project. Some project information may not be available from the controller, and compatibility between the device data and engineering software must be considered.

### 4.3 Application Activation

Transferring an application does not necessarily mean it is already executing. The runtime may need to load the application, initialize its data, and enter the appropriate operating state before normal execution begins.

The exact activation procedure depends on the controller and runtime. CODESYS, for example, provides engineering commands for downloading and starting an application on a connected controller [4]. This connects the engineering lifecycle to the execution lifecycle examined in Investigation 04.

## 5. Online Monitoring and Modification

Engineering environments can establish online connections to controllers to inspect application behavior and interact with running applications. Online operations provide visibility into the deployed system and allow engineers to perform selected changes.

### 5.1 Online Monitoring

Monitoring displays live values and execution information from the connected controller.

Common monitoring capabilities include:

- Viewing current variable values.
- Observing program execution.
- Monitoring function-block states.
- Inspecting I/O values.
- Monitoring task and runtime information.
- Identifying application and controller errors.

Monitoring is generally observational. It provides information about the running application without intentionally changing its program execution.

TIA Portal provides watch tables and program monitoring features for inspecting live PLC values [5].

### 5.2 Modifying Values

Engineering environments may allow engineers to write selected variable values to a running controller.

A modification changes the current value of a variable or data item. Depending on the platform and variable, this may affect application behavior immediately or during subsequent execution. This is different from editing and deploying the program source.

TIA Portal supports modifying selected tag values through its watch table functionality [5].

### 5.3 Forcing Values

Forcing is a separate mechanism that holds a supported variable or I/O point at a specified value according to the controller's force mechanism. It is commonly used during testing and troubleshooting, but can directly influence the physical process.

For example, forcing an output may cause an actuator to operate independently of the value calculated by the normal application logic.

TIA Portal provides separate watch and force table capabilities, with different supported operations [5].

Monitoring, modifying, and forcing should therefore be treated as distinct engineering operations. Online control functions require particular care because they can affect the running program and connected equipment.

## 6. Online Changes and Full Downloads

Modifying the application source is different from modifying a live variable. Changes to the application must be transferred to the controller before they become part of the deployed program. Engineering environments may support different deployment methods depending on the scope of the modification and the target platform.

### 6.1 Full Download

A full download transfers the application to the controller and replaces the previously deployed application or relevant project data.

Depending on the platform, this can involve:

- Recompiling the application.
- Stopping the current application.
- Transferring generated code.
- Reinitializing application data.
- Restarting the application.

CODESYS documents that a normal application download stops the running program and establishes a new application state through reinitialization [6].

Siemens documents different download operations for its controllers. In TIA Portal, downloading all software objects resets their values to initial values, including retentive values [1].

The effect on application state therefore depends on the selected operation, controller, and runtime.

### 6.2 Online Change

An online change transfers selected modifications to an application that is already running.

CODESYS documents online change as a process that transfers modified application parts without stopping the running program [7].

However, an online change does not mean that every modification can be applied without interruption or side effects.

For example:

- Some project changes prevent online change and require a full download.
- Application-specific initialization routines are not executed during the documented online change process.
- Changes to function-block interfaces or data structures may affect existing application data.
- Existing application state may not be appropriate for the modified logic.

CODESYS also documents a fast online change mechanism for certain minor modifications. In that case, only modified POUs are compiled and transferred, and initialization code is not generated [7].

The engineer must understand how a modification affects the running application and its current state.

### 6.3 Platform-Specific Behavior

The availability and behavior of online changes depend on the controller, runtime, firmware, and engineering environment.

Siemens also documents downloading selected program changes while certain CPUs remain in RUN mode. This capability has platform-specific prerequisites and restrictions [8].

It should not be assumed that all PLCs support online modification or that every type of change can be deployed without stopping execution.

### 6.4 Operational Considerations

Before modifying a running application, relevant considerations include:

- Whether the process can tolerate the change.
- Whether the modification affects control outputs.
- Whether the application requires reinitialization.
- Whether existing variable values remain valid.
- Whether the controller supports the selected deployment method.
- Whether a rollback copy of the previous application is available.

Online modification is an engineering capability, not a guarantee of uninterrupted or risk-free deployment.

## 7. Version Management and Project Comparison

PLC projects evolve over time as control logic, hardware configuration, and operational requirements change. Version management helps maintain a history of these changes and identify which application revision is intended for deployment.

### 7.1 Project Version Management

A project revision can represent a particular state of the engineering project.

Version management may record:

- Source code changes.
- Program and function-block revisions.
- Hardware and I/O configuration changes.
- Library and dependency versions.
- Engineering software and target information.
- Change descriptions and approval information.

For industrial automation projects, preserving this information helps engineers understand how the controller's configuration and application have evolved.

### 7.2 External Version Control

Some engineering environments provide mechanisms for integrating project objects with external version-control systems.

TIA Portal's Version Control Interface (VCI), for example, connects TIA Portal to an external version-control program through a local workspace [9].

The workflow involves exporting supported project objects to the workspace. The external version-control program manages the exported files, while TIA Portal provides synchronization mechanisms to identify and reconcile differences.

Supported PLC objects include:

- Organization blocks.
- Function blocks.
- Functions.
- Data blocks.
- PLC data types.
- PLC tag tables.
- Technology objects.

Not every project object can be synchronized through VCI. Siemens documents limitations for certain protected objects, library types, and other object categories [9].

This matters: VCI supports versioning selected project objects, not automatic version control of every component of the complete engineering project.

### 7.3 Project Revision History

A version-control system can preserve project revisions and provide a history of changes. This allows engineers to identify when an application object changed, compare revisions, and retrieve earlier versions when necessary. The exact history and rollback capabilities depend on the external version-control system and the engineering environment.

Version history alone does not establish which revision is currently deployed. The project must still be compared with the connected controller.

### 7.4 Online and Offline Comparison

The engineering project saved on a workstation may differ from the application deployed on the controller. Online/offline comparison tools help identify these differences.

TIA Portal provides comparison functionality for supported PLC project data and connected devices [10].

Its comparison methods include:

- **Offline/online comparison:** compares project objects with corresponding objects on the connected device.
- **Offline/offline comparison:** compares objects between projects or libraries.
- **Detailed comparison:** displays differences within supported objects, such as program blocks.

Comparison results can help identify changes made in the engineering project but not downloaded, as well as differences between the saved project and the controller.

The comparison is limited to supported object types and available project data. It should not be interpreted as proof that every aspect of the controller's operational state has been compared.

### 7.5 Project Portability

IEC 61131-10:2019 defines an XML-based exchange format for exporting and importing IEC 61131-3 projects between programming environments [11].

The format supports the exchange of configuration elements, data types, and POUs written in the programming languages covered by the specification.

This provides a standardized mechanism for project exchange, but it does not guarantee identical compilation or execution across different vendors. Target hardware, runtime capabilities, libraries, and vendor-specific extensions can still affect project portability.

## 8. Backups and Recovery

Backups preserve the information required to restore an engineering project or operational system after accidental changes, equipment failure, corruption, or other disruptions.

For PLC environments, backing up the source program alone may not be sufficient.

### 8.1 Project Archives

A project archive packages an engineering project and associated resources into a transferable file.

For example, TIA Portal creates compressed or uncompressed project archives. Siemens documents that a compressed archive contains the complete project directory, with files reduced to essential components to save space [12].

The archive operation uses the most recently saved state of the project. The project should therefore be saved before creating an archive if the latest changes need to be preserved.

CODESYS also provides project archive functionality for collecting project source and associated resources.

A project archive is useful for preserving and transferring an engineering project, but it should not automatically be treated as a complete backup of the PLC, runtime, or host environment.

### 8.2 Source Code Stored on the Controller

Some engineering environments support storing a project archive on the PLC so that it can be retrieved later.

CODESYS provides source download and source upload functionality. An engineer can transfer a project archive to a controller and later retrieve it through the engineering environment [13]. This can help with maintenance when the original engineering workstation or project copy is unavailable.

However, the feature depends on the source archive having been transferred to the controller. It should not be assumed that every PLC automatically stores the complete engineering project.

OpenPLC Editor v4.3.0 release notes also document a **Retrieve Project from PLC** feature. The release notes state that the device keeps a copy of the source project it is running, allowing the project to be retrieved through the Editor [14].

This is a documented Editor feature. Its presence should not be assumed for every earlier Editor or Runtime version without checking compatibility.

Such capabilities are useful recovery aids, but they do not replace independent backups.

### 8.3 Backup Scope

A recoverable PLC environment may require several types of information:

| Backup item | Purpose |
|---|---|
| Engineering project | Preserves application source and project structure. |
| Compiled application | Preserves a known deployed executable where supported. |
| Hardware configuration | Preserves device and I/O configuration. |
| Libraries and dependencies | Provides resources required to rebuild the application. |
| Firmware and runtime information | Identifies the target software environment. |
| Engineering toolchain information | Helps reproduce the original development and compilation environment. |
| Controller configuration | Preserves relevant communication and operational settings. |
| Host or deployment configuration | Supports recovery of software PLCs and their hosting environments. |

The exact backup scope depends on the PLC architecture and operational requirements.

NIST SP 800-82 Rev. 3 recommends maintaining backups of relevant OT system state, data, configuration files, and programs at regular intervals to support recovery to a stable state [15].

It also identifies backup integrity, secure storage, and restoration testing as important considerations. Its backup guidance includes maintaining an inventory of backups and verifying their reliability and integrity where technically possible [15].

### 8.4 Recovery and Restoration

Recovery involves restoring a known-good application and its associated configuration.

A general restoration process may involve:

1. Identifying the required backup revision.
2. Confirming compatibility with the target controller and runtime.
3. Restoring the engineering project and dependencies.
4. Rebuilding the application if required.
5. Transferring the application and configuration to the target.
6. Verifying the deployed application.
7. Confirming expected controller and process behavior before returning to normal operation.

Restoring the program alone may not restore the complete operational environment. Hardware configuration, firmware, libraries, communication settings, and retained application data may also influence recovery.

NIST emphasizes that OT recovery planning must consider human and environmental safety before restarting operations. Restoration procedures should be established and tested at intervals appropriate to the organization [15].

## 9. Engineering-to-Runtime Relationship

The engineering environment and PLC runtime represent different parts of the application lifecycle. The engineering environment develops and prepares the application. The runtime receives the application, loads it, initializes it, and executes it.

A simplified relationship is:

```text
┌─────────────────────────────┐
│     Engineering Environment │
│                             │
│  Project Development        │
│  Configuration              │
│  Compilation                │
│  Testing and Validation     │
└──────────────┬──────────────┘
               │
               │ Program Transfer
               ▼
┌─────────────────────────────┐
│          PLC Runtime        │
│                             │
│  Application Loading        │
│  Initialization             │
│  Program Execution          │
│  I/O Coordination           │
│  Diagnostics                │
└──────────────┬──────────────┘
               │
               │ Online Connection
               ▼
┌─────────────────────────────┐
│     Engineering Operations  │
│                             │
│  Monitoring                 │
│  Value Modification         │
│  Online Change              │
│  Project Comparison         │
└─────────────────────────────┘
```

The online connection provides a path for engineering tools to inspect and interact with the deployed application. Depending on the platform, it may also support application transfer and modification.

### 9.1 Different Representations of an Application

It is useful to distinguish four representations throughout the lifecycle.

| Representation | Description |
|---|---|
| Engineering project | Source logic, device configuration, task settings, data types, and dependencies. |
| Build output | Generated code and other executable data produced by the compilation process. |
| Deployed application | Application currently loaded or executing on the PLC runtime. |
| Archived or backup copy | Preserved project or system state intended for revision history or recovery. |

These representations are related, but they are not necessarily identical.

A compiled executable may not contain all the engineering information required to recreate the original project. A backup may preserve an older project revision that no longer matches the deployed controller. An upload may recover selected controller data without reconstructing every original project object.

Maintaining consistency between these representations is an important part of PLC engineering and maintenance.

### 9.2 Engineering Access as an Operational Control Point

The engineering workstation provides capabilities that can affect the controller and its physical process.

Through supported engineering interfaces, an operator or engineer may be able to:

- Modify application logic.
- Transfer a new application.
- Change variable values.
- Force supported I/O points.
- Change controller configuration.
- Retrieve project data.
- Compare online and offline application states.

These capabilities make engineering access an important operational control point.

The ability to modify a running PLC application is especially significant because changes can affect the behavior of the physical process. Engineering access, project transfer, and online modification should therefore be managed according to the operational requirements of the system.

NIST SP 800-82 Rev. 3 discusses OT configuration management as a way to maintain consistent system configurations and track changes throughout the system lifecycle. It recommends documenting approved baselines and testing, validating, and approving changes before deployment [15].

## 10. Technical Assessment

PLC engineering is a continuous lifecycle that extends beyond writing and compiling control logic. The engineering environment manages the project and its configuration, while the runtime receives and executes the deployed application.

Program transfer connects these environments. Online monitoring provides visibility into the deployed application, while value modification, forcing, and online changes provide different levels of interaction with the running controller.

Version management and project comparison help maintain consistency between engineering revisions and deployed applications. Backups and recovery procedures preserve the information needed to restore a known-good state.

The distinction between the engineering project and deployed application is particularly important. A saved project does not automatically represent the controller's current state, and an application retrieved from a controller may not contain everything needed to recreate the original engineering environment.

For software PLCs, the same lifecycle applies, but additional deployment components may be involved. The engineering environment, compilation process, management interface, runtime, and host environment can all contribute to the final operational system.

Understanding these relationships establishes a foundation for examining how engineering access and application changes influence software PLC security.
