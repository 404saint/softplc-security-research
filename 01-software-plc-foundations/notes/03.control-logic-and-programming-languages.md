# Industrial Control Logic and Programming Languages

**Research Area:** Software PLC Foundations 
**Investigation:** 03 
**Document Type:** Technical Research Report
**Research Focus:** Industrial control logic representation, programming, and organization within PLC applications.

---
## 1. Scope and Context

Industrial control applications describe how a controller responds to process inputs, evaluates operating conditions, maintains internal states, and produces control outputs. IEC 61131-3 provides a standardized programming model for expressing this behavior through a defined set of programming languages and program organization elements.

The purpose of this investigation is to understand how industrial control logic is represented and organized, with particular attention to the relationship between programming languages, variables, reusable logic components, and application execution.

The primary reference is IEC 61131-3:2025, Edition 4.0. Vendor documentation is used to explain practical language constructs and programming examples. Implementation-specific behavior is identified where relevant.

## 2. IEC 61131-3

### 2.1 Purpose and Scope

IEC 61131-3 specifies the syntax and semantics of programming languages for programmable controllers defined in IEC 61131-1.

Its scope extends beyond individual language syntax. It also defines elements used to organize programs and function blocks, configure their installation within controller systems, and support communication between programmable controllers and other automation-system components [1].

The standard provides a common programming model that allows control applications to be developed using a consistent set of language constructs and organization principles.

It does not prescribe a particular PLC hardware architecture, runtime implementation, operating system, or engineering environment.

### 2.2 Programming Languages

The 2025 edition defines three programming languages:

| Language                     | Representation | Main purpose                                                                           |
|------------------------------|----------------|----------------------------------------------------------------------------------------|
| Ladder Diagram (LD)          | Graphical      | Representing Boolean and discrete control logic through contact and coil elements      |
| Function Block Diagram (FBD) | Graphical      | Representing logic and processing through interconnected functions and function blocks |
| Structured Text (ST)         | Textual        | Expressing calculations, conditions, algorithms, and structured control logic          |

Sequential Function Chart (SFC) provides additional graphical and equivalent textual elements for structuring the internal organization of programs and function blocks. It is therefore important to distinguish its organizational role from the three programming languages listed above [1][2].

### 2.3 Standard Evolution

Earlier editions included Instruction List (IL), a textual language based on instruction sequences. IEC 61131-3:2013 included IL alongside ST, LD, and FBD.

The fourth edition, published in May 2025, no longer includes IL in its current language suite. It also introduces UTF-8 strings and associated functions and provides an informative annex identifying features added, removed, or deprecated compared with the previous edition [1][2].

Legacy engineering environments may still support IL. Its availability in a particular tool should not be interpreted as its inclusion in the current IEC 61131-3 language suite.

## 3. Industrial Control Programming Languages

### 3.1 Ladder Diagram (LD)

Ladder Diagram is a graphical programming language based on the visual representation of relay control circuits.

Its appearance is built around two vertical power rails connected by horizontal networks, commonly called rungs. Each network contains logical elements that evaluate Boolean conditions and determine the state assigned to output variables [3].

The principal elements include:

| Element                    | Purpose                                                                             |
|----------------------------|-------------------------------------------------------------------------------------|
| Normally open contact      | Evaluates a Boolean variable and passes the logical state when the variable is TRUE |
| Normally closed contact    | Evaluates the inverse of a Boolean variable                                         |
| Coil                       | Assigns a Boolean result to an associated variable                                  |
| Branch                     | Represents parallel logical paths                                                   |
| Function or function block | Incorporates reusable processing logic into a network                               |

Contacts connected in series represent an AND relationship. Parallel branches represent an OR relationship. Negated contacts represent the inverse of a condition.

For example, a motor command may depend on a start condition and an operating permissive. These conditions can be represented as contacts in a ladder network.

**Characteristics:**

- Provides a visual representation of Boolean control relationships.
- Resembles traditional relay-control diagrams.
- Makes discrete control conditions relatively easy to inspect.
- Supports function and function-block calls within its networks.

An important distinction is that ladder contacts and coils are programming elements. A contact does not necessarily represent a physical switch, and a coil does not necessarily represent a physical relay. They operate on variables within the controller application. Physical I/O is handled through the controller's I/O configuration and mapping.

### 3.2 Function Block Diagram (FBD)

Function Block Diagram is a graphical programming language in which control logic is represented through interconnected blocks.

Each block performs an operation and exposes inputs and outputs. Connecting lines establish relationships between variables and processing elements. A network may contain logical expressions, arithmetic operations, and calls to functions or function blocks [3].

The typical signal flow within an FBD network runs from left to right, although the visual presentation and editing conventions depend on the programming environment.

Common applications include:

- Boolean control and interlocking.
- Mathematical calculations.
- Signal processing.
- Analog control functions.
- Combining reusable function blocks.

A motor-control application could use FBD blocks to evaluate start conditions, operating permissives, and the final motor command.

FBD is particularly useful when the relationships between processing elements are easier to understand visually than through textual expressions.

**Characteristics:**

- Represents processing through interconnected blocks.
- Makes relationships between signals and operations visible.
- Supports reusable functions and stateful function-block instances.
- Can organize relatively complex processing without requiring extensive textual code.

### 3.3 Structured Text (ST)

Structured Text is a textual programming language used to express control logic through statements and expressions.

Its syntax resembles conventional high-level programming languages. It supports variable assignments, arithmetic expressions, Boolean operations, conditional execution, loops, and calls to functions and function blocks [4].

Common constructs include:

| Construct           | Purpose                                               |
|---------------------|-------------------------------------------------------|
| Assignment (`:=`)   | Assigns a value to a variable                         |
| `IF`, `ELSIF`, `ELSE` | Conditional execution                               |
| `CASE`              | Selects execution based on a value                    |
| `FOR`               | Repeats statements over a defined range               |
| `WHILE`             | Repeats statements while a condition remains TRUE     |
| `REPEAT`            | Repeats statements until a condition becomes TRUE     |
| Function call       | Executes a reusable operation                         |
| Function-block call | Executes an instance of a reusable stateful component |

A simple example:

```iecst
IF RunPermissive AND StartButton THEN
    MotorCommand := TRUE;
ELSE
    MotorCommand := FALSE;
END_IF;
```

The condition is evaluated as a Boolean expression. When both inputs are TRUE, the motor command is assigned TRUE. Otherwise, it is assigned FALSE.

ST is useful for logic involving multiple conditions, data manipulation, calculations, and algorithms that would be difficult to express clearly through graphical networks.

**Characteristics:**

- Supports structured conditional and sequential statements.
- Allows complex expressions and calculations.
- Supports reusable functions and function blocks.
- Provides a compact textual representation of control logic.

The language's execution remains governed by the controller's program organization and task scheduling. Writing an ST program does not independently determine when or how frequently it executes.

### 3.4 Sequential Function Chart (SFC)

Sequential Function Chart is used to represent control behavior organized into steps and transitions.

Instead of expressing an entire process as a continuous collection of conditions, SFC describes the progression of an application through defined operational stages.

Its main elements are:

| Element          | Purpose                                                        |
|------------------|----------------------------------------------------------------|
| Step             | Represents an operational state or stage                       |
| Transition       | Defines the condition required to move to another step         |
| Action           | Contains the statements or operations associated with a step   |
| Initial step     | Identifies the starting point of the sequence                  |
| Action qualifier | Defines how an associated action behaves during step execution |

A basic sequence might represent:

1. Idle: The motor is stopped and waiting for a start command.
2. Starting: The controller issues a start command.
3. Running: The motor is operating.
4. Stopping: The controller removes the run command.
5. Fault: An abnormal condition requires a different operational response.

Transitions determine when the sequence advances. For example, the transition from Idle to Starting may depend on a start request and the required operating permissives.

Actions contain the logic executed in association with their steps. They can be written using supported IEC programming languages, including ST.

SFC also supports action qualifiers. These determine how actions behave in relation to the active state of their associated steps.

| Qualifier | Name                    | General behavior                                                              |
|-----------|-------------------------|-------------------------------------------------------------------------------|
| N         | Non-stored              | Action executes while its associated step is active.                          |
| R         | Reset                   | Deactivates an action previously set using a stored qualifier.                |
| S         | Set (Stored)            | Action remains active after its associated step becomes inactive until reset. |
| L         | Time Limited            | Action executes while the step is active, subject to a specified time limit.  |
| D         | Time Delayed            | Action starts after a specified delay if the step remains active.             |
| P         | Pulse                   | Action executes when the associated step becomes active.                      |
| SD        | Stored and Time Delayed | Action starts after a delay and remains stored until reset.                   |
| DS        | Delayed and Stored      | Action becomes stored after the specified delay, provided the step remains active until then. |
| SL        | Stored and Time Limited | Action remains stored for a specified time or until reset.                    |

The time-related qualifiers require an associated time parameter. PLCopen's SFC guidelines provide the general qualifier definitions and describe their relationship with step execution [5].

Implementation details can differ. For example, CODESYS documents that an IEC action is executed once more when it is deactivated. It also describes its P qualifier as executing an action on both step activation and deactivation. This behavior should be understood as part of the documented CODESYS execution model, rather than generalized to every SFC implementation [6].

**Characteristics:**

- Makes sequential process behavior easier to follow.
- Separates operational stages from the conditions that connect them.
- Supports actions implemented in other PLC programming languages.
- Is useful for machine sequences, startup procedures, operating modes, and fault-handling sequences.

SFC does not replace ST, LD, or FBD. It provides a way to organize the execution of control behavior into a sequence.

## 4. Variables and Data Types

### 4.1 Variables

A variable is a named storage location used by a PLC application to represent a value.

Every variable is declared with a data type. The type determines the values that can be represented, how the controller interprets the stored value, and which operations are valid for it [7].

Variables can represent:

- Physical process inputs.
- Control outputs.
- Internal application state.
- Setpoints and measured values.
- Timers and counters.
- Communication data.

Variables are commonly declared in a POU's declaration section or in a global variable list.

IEC-style declarations include:

| Declaration  | Purpose                                                                 |
|--------------|-------------------------------------------------------------------------|
| `VAR_INPUT`  | Declares values supplied to a POU                                       |
| `VAR_OUTPUT` | Declares values produced by a POU                                       |
| `VAR_IN_OUT` | Declares values that can be read and modified through the POU interface |
| `VAR`        | Declares internal variables                                             |
| `VAR_GLOBAL` | Declares variables in a global variable list                            |

`VAR_GLOBAL` is used to declare variables in a global variable list rather than serving as an ordinary local declaration section inside every POU. These variables can be accessed by other application components within the configured scope.

The exact availability and behavior of declaration features can depend on the programming environment and target implementation.

### 4.2 Data Types

IEC 61131-3 defines data types used to represent different categories of information.

| Category          | Examples                         | Typical use                                     |
|-------------------|----------------------------------|-------------------------------------------------|
| Boolean           | `BOOL`                           | Digital states and logical conditions           |
| Signed integers   | `SINT`, `INT`, `DINT`, `LINT`    | Numeric values that can be positive or negative |
| Unsigned integers | `USINT`, `UINT`, `UDINT`, `ULINT`| Non-negative integer values                     |
| Real numbers      | `REAL`, `LREAL`                  | Measurements, setpoints, and calculations       |
| Bit strings       | `BYTE`, `WORD`, `DWORD`, `LWORD` | Bit-level values and packed status information  |
| Time              | `TIME`, `LTIME`                  | Durations and time intervals                    | 
| Date and time     | `DATE`, `TOD`, `DT`              | Dates, times of day, and date-time values       |
| Character strings | `STRING`, `WSTRING`              | Textual information                             |

Additional types can be constructed from existing types, including arrays, structures, enumerations, and subranges. The 2025 edition also includes UTF-8 strings and associated functions [1].

The exact set of available types can vary between programming systems. Some environments also provide vendor-specific extensions, so a type supported by one development environment should not automatically be assumed to be portable across all IEC 61131-3 implementations [7][8].

Selecting an appropriate data type is important. For example, `BOOL` is appropriate for a motor command, whereas an analog temperature measurement would normally require a numeric type such as `REAL`.

### 4.3 Variable Initialization and Retention

Variables can have initial values assigned during declaration.

For example:

```iecst
VAR
    MotorLatched : BOOL := FALSE;
    MotorSpeed   : REAL := 0.0;
END_VAR
```

Initialization defines the value used when the variable is initialized by the runtime.

Ordinary variable retention during repeated program execution should be distinguished from retention across controller restarts or power loss. Retentive and persistent variable mechanisms may be available, but their exact behavior depends on the controller and runtime implementation.

### 4.4 Global and Local Variables

Local variables belong to the POU in which they are declared. They are generally used for data required only within that program, function, or function block.

Global variables are declared in a global variable list and can be accessed by multiple POUs within their configured scope.

Global variables can simplify data sharing, but they also introduce dependencies between application components. Excessive use can make it harder to understand which parts of an application modify a particular value.

## 5. Functions and Function Blocks

Functions and function blocks are reusable programming components. Both can be called from other POUs, but their behavior and state management differ.

### 5.1 Functions

A function is a POU that produces a return value when executed.

It can receive input parameters, perform an operation, and return a result. In textual languages such as ST, a function can be used within an expression.

Example:

```iecst
FUNCTION CalculateDifference : INT

VAR_INPUT
    ValueA : INT;
    ValueB : INT;
END_VAR

CalculateDifference := ValueA - ValueB;

END_FUNCTION
```

The function can then be called from another POU:

```iecst
Difference := CalculateDifference(
    ValueA := 20,
    ValueB := 8
);
```

The primary result is returned through the function name. IEC function declarations can also support additional output parameters.

Functions do not have independently instantiated, retained state in the way function blocks do. Their results are produced from the supplied arguments and the operations performed during the call [9].

### 5.2 Function Blocks

A function block is a reusable POU that can maintain internal data between calls.

Unlike a function, a function block is declared as a type and must be called through an instance. Each instance maintains its own internal state and output values [10].

Example:

```iecst
VAR
    StartEdge : R_TRIG;
END_VAR
```

Here, `R_TRIG` is a function-block type and `StartEdge` is an instance of that type.

It can be called as follows:

```iecst
StartEdge(CLK := StartButton);
```

Its output can then be accessed through:

```iecst
IF StartEdge.Q THEN
    MotorLatched := TRUE;
END_IF;
```

`R_TRIG` detects a rising edge on its input. Its `Q` output becomes TRUE for the execution in which the rising edge is detected [12].

Other common function-block examples include:

- `TON`: On-delay timer.
- `TOF`: Off-delay timer.
- `TP`: Pulse timer.
- `CTU`: Up-counter.
- `CTD`: Down-counter.
- `RS` and `SR`: Bistable elements.

### 5.3 Function vs. Function Block

| Characteristic            | Function                                               | Function Block                                         |
|---------------------------|--------------------------------------------------------|--------------------------------------------------------|
| Main purpose              | Performs an operation and returns a result             | Performs an operation that may maintain internal state |
| Declaration               | Defined using `FUNCTION`                               | Defined using `FUNCTION_BLOCK`                         |
| Instance required         | No independent instance required                       | Yes                                                    |
| Internal persistent state | No per-instance retained state                         | Yes                                                    |
| Outputs                   | Primary return value, with possible additional outputs | One or more output variables                           |
| Typical examples          | Mathematical and conversion operations                 | Timers, counters, edge detectors                       |

This distinction is important when analyzing PLC applications. A function block does not merely represent a reusable block of code. Its instance contains data that influences subsequent executions.

## 6. PLC Application Organization

IEC 61131-3 provides organizational elements that allow a controller application to be divided into manageable components.

### 6.1 Program Organization Units (POUs)

A Program Organization Unit (POU) is a logical unit containing a declaration interface and an implementation.

The principal POU types are:

| POU            | Description                                                                                    |
|----------------|------------------------------------------------------------------------------------------------|
| Program        | Organizes an application component that is called through the controller's task configuration  |
| Function       | Performs an operation and returns a result                                                     |
| Function Block | Encapsulates processing logic and associated instance data                                     |

POUs can be implemented using supported IEC programming languages. This allows an application to combine ST, LD, and FBD where appropriate.

For example, an ST program may manage motor operation while calling standard function-block instances for edge detection and timing.

### 6.2 Configuration and Tasks

A controller application needs more than program source code. Its execution must also be configured.

The IEC programming model includes configuration elements that describe how programs are installed and executed within a programmable controller system.

A typical conceptual organization is:

```text
PLC Configuration
│
└── Resource / Controller Execution Environment
    │
    ├── Task: MainCycle
    │   │
    │   └── Program: MotorControl
    │       │
    │       ├── Function Block: StartEdge
    │       └── Internal Variables
    │
    └── I/O Configuration
        │
        └── MotorCommand → Physical Output
```

A task defines the execution flow for the programs assigned to it. Common task types documented by CODESYS include:

- **Cyclic:** Executes according to a configured cycle interval.
- **Freewheeling:** Repeats execution continuously, subject to the runtime's scheduling behavior.
- **Event-triggered:** Executes in response to a configured event.
- **Status-triggered:** Executes while a configured Boolean status condition is TRUE.

These are examples of task types supported by CODESYS, not a requirement that every IEC 61131-3 implementation provide precisely the same task options. Task scheduling, priorities, cycle intervals, and watchdog behavior depend on the controller runtime and target configuration [11].

A POU being present in a project does not by itself establish when it will execute. Its place in the application's task and call structure must also be considered.

### 6.3 POU Relationships

POUs can call other POUs to create a structured application.

A program may call a function to perform a calculation or call a function-block instance to perform a stateful operation. This allows developers to separate application responsibilities instead of placing all control logic inside one large program.

A possible organization for a motor-control application could include:

| Component         | Responsibility                             |
|-------------------|--------------------------------------------|
| `MotorControl`    | Coordinates motor operation                |
| `StartEdge`       | Detects a new start command                |
| `MotorTimer`      | Manages a configured timing requirement    |
| `MotorStatus`     | Provides motor operating-state information |
| `MotorInterlocks` | Evaluates operating permissives            |

This is an illustrative application structure rather than a mandatory IEC arrangement.

### 6.4 Physical I/O Mapping

Application variables and physical controller terminals are related through the controller's hardware and I/O configuration.

For example, a program may declare:

```iecst
MotorCommand : BOOL;
```

This declaration creates a logical output variable. It does not automatically connect the variable to a physical digital output terminal.

The engineering environment must establish the appropriate mapping between application variables and the controller's I/O channels. The details differ between platforms. This is important when examining the boundary between application logic and the physical process.

## 7. Reference Application: Motor Start/Stop Control

The following example provides a common reference for the concepts discussed in this investigation.

```iecst
PROGRAM MotorControl

VAR_INPUT
    StartButton     : BOOL;
    StopPermissive  : BOOL;
    RunPermissive   : BOOL;
END_VAR

VAR_OUTPUT
    MotorCommand    : BOOL;
END_VAR

VAR
    StartEdge       : R_TRIG;
    MotorLatched    : BOOL := FALSE;
END_VAR

(* Detect a rising edge on the start button *)
StartEdge(CLK := StartButton);

(* Evaluate motor operating conditions *)
IF (NOT StopPermissive) OR (NOT RunPermissive) THEN
    MotorLatched := FALSE;

ELSIF StartEdge.Q THEN
    MotorLatched := TRUE;
END_IF;

(* Publish the motor command *)
MotorCommand := MotorLatched;

END_PROGRAM
```

### 7.1 Program Structure

The example is declared as a `PROGRAM` POU and implemented using Structured Text.

Its inputs and outputs define the interface between the program and other application components. Internal variables hold the state and function-block instance required by its logic.

### 7.2 Control Logic

The application evaluates two operating permissives before accepting a start command.

If either permissive is FALSE, the motor's latched command is reset. If both permissives are TRUE and a rising edge is detected on the start button, the motor state is set to TRUE.

The final assignment transfers the internal state to the logical output variable.

### 7.3 Concepts Demonstrated

| Concept                   | Implementation                                   |
|---------------------------|--------------------------------------------------|
| Program POU               | `PROGRAM MotorControl`                           |
| Boolean variables         | `StartButton`, `StopPermissive`, `RunPermissive` |
| Output variable           | `MotorCommand`                                   |
| Internal state            | `MotorLatched`                                   |
| Function-block type       | `R_TRIG`                                         |
| Function-block instance   | `StartEdge`                                      |
| Function-block invocation | `StartEdge(CLK := StartButton)`                  |
| Conditional logic         | `IF`, `ELSIF`, `END_IF`                          |
| Boolean operators         | `NOT`, `OR`                                      |
| Assignment                | `:=`                                             |

The `StartEdge` instance remembers the previous state of its input so it can detect a rising transition. The `MotorLatched` variable retains its value across successive program executions while the application continues running. This does not automatically imply retention across a controller restart or power loss.

The program must be assigned to an appropriate controller task to execute. Its logical output must also be mapped to a physical output if it is to control an actual device.

This example is intended for understanding ordinary application logic. It is not a safety-rated motor-control or emergency-stop implementation. Safety-related functions require an appropriately engineered safety system.

## 8. Technical Assessment

IEC 61131-3 provides a common model for expressing and organizing industrial control applications.

LD, FBD, and ST offer different ways to represent the same broad category of control behavior. LD presents Boolean logic through relay-style networks. FBD presents processing through connected blocks. ST expresses logic through textual statements and expressions. SFC helps organize programs around sequential stages and transitions.

Variables and data types define how application information is represented. Functions and function blocks provide reusable processing components, with function-block instances maintaining their own state. Programs, tasks, and configuration elements establish how these components are organized and executed.

These elements are closely related. Understanding a control application's source code alone is insufficient to understand its behavior. Its POU relationships, variable interfaces, task configuration, I/O mapping, and runtime implementation must also be considered.

Finally, standardization does not guarantee identical implementation across all PLC platforms. Supported language features, libraries, I/O configuration, task scheduling, and runtime behavior can vary. These differences are important when assessing application portability and controller behavior.
